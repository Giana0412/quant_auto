## 2. 🔴 충돌 1건 — Claude 계정

**어제 결정:** 회사용 Claude 계정 1개를 공용으로 쓴다.
**회의 #2:** Claude 계정 종속 설계는 피해야 한다. 개인 토큰·계정값은 각자 로컬로 분리한다.

이 둘은 **두 개의 서로 다른 축**이 겹쳐 있다. 나눠서 보면 하나는 풀리고 하나는 남는다.

### 축 A — 커넥터 (풀린다)

이준범님 우려의 핵심은 **claude.ai 커넥터가 Claude에만 묶인다**는 것이다. 맞는 지적이다.
그런데 **해법이 이미 이 레포 안에 있다.**

```
지금 (회사 캘린더)                          개인 캘린더 — 이미 이 방식으로 돌고 있음
────────────────────────                   ────────────────────────────────────
claude.ai 커넥터                            로컬 MCP 서버
mcp__claude_ai_Google_Calendar__*           mcp__google-calendar-personal__*
        │                                           │
   Claude 계정에 묶임                        ~/.config/google-calendar-mcp/
   → 다른 LLM으로 못 옮김                    로컬 OAuth 토큰
                                            → MCP 지원하는 어떤 클라이언트든 씀
```

**회사 캘린더도 로컬 MCP 서버 방식으로 바꾸면** 우려 두 개가 동시에 해소된다.

| 우려 | 로컬 MCP로 바꾸면 |
|---|---|
| LLM 종속 | ✅ 해소 — MCP는 모델 중립. GPT·Gemini 클라이언트도 같은 서버를 쓴다 |
| 개인 토큰이 공용 계정에 붙음 | ✅ 해소 — 토큰이 계정이 아니라 **기기**에 있다 |

그리고 어제 §1-7에 세운 규칙("공용 계정에 붙인 커넥터는 전원이 접근한다")이
**아예 무력화된다.** 커넥터가 계정에 안 붙으므로 그 위험 자체가 사라진다.

> 실무 부담도 작다. 커넥터가 필요한 기기는 **자동화 머신 1대뿐**이다
> (팀원은 0개 — [[전체-구조도]] §1-5에서 확인). 그 1대에 OAuth를 한 번 붙이면 끝난다.

**[제안] 회사 캘린더를 claude.ai 커넥터 → 로컬 MCP 서버로 전환한다.**

### 축 B — 좌석 (남는다)

"개인 계정값은 각자 로컬로 분리"는 **각자 계정을 갖는 것**을 함의한다.
공용 1계정과 정면으로 부딪히고, 이건 기술이 아니라 **비용 결정**이라 사람이 정해야 한다.

| | 공용 1계정 | 각자 계정 |
|---|---|---|
| 비용 | 1석 | N석 |
| 사용량 한도 | 전원이 나눠 씀 | 각자 |
| 누가 무엇을 했는지 | 구분 안 됨 | 구분됨 |
| 회의 #2 정합성 | ✗ | ✓ |

> **커넥터를 로컬 MCP로 옮기면 축 B의 시급성은 크게 낮아진다.**
> 계정 공유의 가장 큰 위험(전원이 남의 메일함·일정을 봄)이 커넥터에서 나왔기 때문이다.
> 그래도 사용량·추적·약관 문제는 남는다. → §7 D1

## 3. 과제 1 — raw / wiki / schema 재설계

> ✅ **2026-08-12 실행 완료.** 아래 §3-2 제안대로 이사했다 (문서 54개, git mv 로
> 이력 보존). 링크는 이사 전에 짧은 이름으로 통일해 하나도 깨지지 않았다.
> 실제 구조와 층별 권한은 [[전체-구조도]] §3-1 참조.
>
> 제안과 달라진 점 2가지:
> - `07-persona` → `wiki/04-persona`, 회의록 → `wiki/05-meetings/` 로 **번호를 다시 매겼다**
>   (04·05·06 이 빠져나가 번호에 구멍이 생겼기 때문)
> - 정리본·결정사항을 한 폴더로 합치지 않고 **하위 폴더로 유지**했다
>   (STAGE2 가 결정사항만 훑어야 하므로)

### 3-1. 현재 구조를 그 축으로 재분류하면

```
                    현재 폴더                        이준범 축
  ┌──────────────────────────────────────────┬─────────────────┐
  │ vault/raw/slack/              (5)         │  raw            │
  │ vault/raw/transcripts/      (6)         │  raw     ← ⚠️   │
  ├──────────────────────────────────────────┼─────────────────┤
  │ vault/wiki/05-meetings/정리본/      (7)         │  wiki           │
  │ vault/wiki/05-meetings/결정사항/    (6)         │  wiki           │
  │ vault/wiki/00-overview/           (4)         │  wiki           │
  │ vault/wiki/01-architecture/       (5)         │  wiki           │
  │ vault/wiki/02-modules/            (6)         │  wiki           │
  │ vault/wiki/03-notes/questions.md  (1)         │  wiki           │
  │ vault/wiki/04-persona/            (3)         │  wiki           │
  ├──────────────────────────────────────────┼─────────────────┤
  │ vault/schema/템플릿-가이드.md (1)        │  schema  ← 유일  │
  ├──────────────────────────────────────────┼─────────────────┤
  │ vault/log/session-log.md (1)         │  log            │
  ├──────────────────────────────────────────┼─────────────────┤
  │ (없음)                                    │  index   ← 부재  │
  └──────────────────────────────────────────┴─────────────────┘
```

**⚠️ 이준범님이 "분리가 약하다"고 본 지점의 구체적 정체가 이것이다.**
`01-전사본`은 raw인데 `02-정리본`·`03-결정사항`(wiki)과 **같은 부모 폴더 안에** 있다.
성격이 다른 두 층이 `06-docs/` 하나에 섞여 있어서, 폴더만 봐서는
"고쳐도 되는 문서"와 "손대면 안 되는 원본"이 구분되지 않는다.

**index가 없다는 것도 이미 증상으로 나타나 있었다.** `_템플릿-가이드.md`가
`[[index]]`를 가리키는데 그 파일이 없다 — 있어야 할 것으로 상정하고
쓴 링크가 깨진 채 남아 있었다 ([[전체-구조도]] §4-1).

### 3-2. [제안] 최상위를 3층으로 가른다

```
vault/
├── raw/          ← 원본. 손대지 않는다. read-only
│   ├── slack/            (← 현 05-slack)
│   └── transcripts/      (← 현 raw/transcripts)
│
├── wiki/         ← 정리된 지식. 에이전트가 고친다. read-write
│   ├── 00-overview/  01-architecture/  02-modules/
│   ├── 03-notes/     07-persona/
│   └── meetings/         (← 현 wiki/05-meetings/정리본, 03-결정사항)
│
├── schema/       ← 분류 체계와 운영 규칙. 사람이 정한다
│   ├── 템플릿-가이드.md        (← 현 schema/템플릿-가이드)
│   ├── 폴더-규칙.md            🆕
│   ├── 프론트매터-규격.md       🆕  ← [[전체-구조도]] §6-2가 초안
│   ├── 링크-규칙.md            🆕  ← [[전체-구조도]] §4-3이 초안
│   └── lint-규칙.md            🆕  ← §4-3
│
├── index/        ← 목차. 에이전트가 자동 생성 🆕
│   ├── 회의.md  결정.md  파트너.md  사람.md
│
└── log/          ← 이력. append-only
    └── session-log.md    (← 현 04-logs)
```

**read-only / read-write 구분이 폴더 하나로 표현된다.** `raw/`는 무슨 일이 있어도
수정·삭제하지 않는다. 이건 규칙일 뿐 아니라 **스킬·스크립트의 쓰기 경로 제한으로
강제할 수 있다** — 이미 `handoff` 스킬이 "`vault/` 밖은 건드리지 않는다"를 하고 있다.

**[미결] 이 이사를 실제로 할 것인가.** 42개 문서를 옮기면 링크 106개 중
상대경로 링크가 깨진다([[전체-구조도]] §4-3의 B형). 이사할 거라면
**짧은 이름 링크로 먼저 통일하고 옮기는 것**이 안전하다. → §7 D2

## 4. 과제 2 — ingest / query / lint 정의

### 4-1. 현재 대응물

| 오퍼레이션 | 현재 있는 것 | 상태 |
|---|---|---|
| **ingest** | `process-slack-docs.sh` 1단계 (raw → 3종 문서) | 🟡 **있으나 Slack 전용**. 일반 raw 파일을 못 받는다 |
| **query** | 페르소나 데모 1회. 헤르메스 미연결 | 🟠 사실상 없음 |
| **lint** | — | 🔴 **전무** |

**ingest는 이미 절반 있다.** `process-slack-docs.sh`의 1단계가 정확히
"raw를 읽어 템플릿대로 wiki를 만드는" 일을 한다. 문제는 입력이
`vault/raw/slack/*.md`로 **고정**돼 있다는 것이다. 회의 `#6`이 말한
"누군가 전사본을 raw에 넣으면"을 받으려면 이 입력을 `raw/` 전체로 넓히면 된다.

→ 즉 **새로 만드는 게 아니라 입력 경로를 일반화하는 작업**이다.

### 4-2. [제안] 세 오퍼레이션의 정의

| | 무엇을 | 언제 | 누가 |
|---|---|---|---|
| **ingest** | `raw/`의 미처리 파일 → `wiki/`에 템플릿대로 정리. 원본은 그대로 둠 | 파일이 들어올 때 (현재는 1시간 폴링) | Hermes |
| **query** | 사람·에이전트의 질문에 `wiki/`를 근거로 답하고 **출처 문서를 링크로 제시** | 요청 시 | Hermes |
| **lint** | `schema/`의 규칙 위반을 찾아 보고. **자동 수정은 하지 않고 목록만** | 주 1회 | Hermes |

> lint가 자동 수정까지 하면 사람이 의도한 예외를 지운다.
> **찾아서 보고까지만** 하고, 고칠지는 사람이 정한다.

### 4-3. lint 규칙 — ✅ 2026-08-12 구현 완료

> **정본은 [[lint-규칙]] 이다.** 아래는 이 문서를 쓸 당시의 초안이며, 구현하면서
> 두 곳이 바뀌었다. 규칙을 확인할 때는 [[lint-규칙]] 을 볼 것.

| # | 초안 | 실제 구현 |
|---|---|---|
| L1 | 깨진 위키링크 | 그대로 |
| L2 | `#숫자+조사` 오인식 태그 | 그대로 |
| L3 | `created`·`updated` 둘 다 필수 | **`created` 만 필수로 축소** |
| L4 | 고아 문서 | 그대로 (`raw/` 는 제외) |
| L5 | `raw/` 불변성 | **→ L6 으로 이동** |
| — | (초안에 없음) | **L5 = 고쳐진 문서에 `updated` 가 있는가** (git 이력 대조) |
| L6 | 회의 3종 상호 링크 | **규칙으로 만들지 않음** — [[회의]] 목차가 빠진 문서를 표시하므로 중복 |
| L7 | `review_by` 경과 | 그대로 |

**L3 을 축소한 이유**: "모든 문서에 `updated` 필수"로 돌렸더니 54개 중 42개가 걸렸다.
회의록처럼 한 번 쓰고 안 고치는 문서에는 `updated` 가 없는 게 정상이다.
**위반이 전체의 절반을 넘으면 문서가 아니라 규칙이 틀린 것**이라, git 이력을 근거로
"실제로 두 번 이상 고쳐진 문서"만 지적하도록 L5 를 새로 만들었다.

**첫 실행 결과: 60건 → 0건.** 상세는 [[lint-규칙]] §3.

## 5. 회의 `#6`과 어제 세일즈 안의 관계 — 충돌하지 않는다

어제 정한 "세일즈 Slack 채널 수집"([[전체-구조도]] §1-8)이 회의 #6
("Slack은 인입의 중심축이 아니다")과 부딪히는 것처럼 보이지만, 실제로는 **같은 구조**다.

```
회의 #6이 말한 기본 흐름          어제 세일즈 안
─────────────────────          ─────────────────
누군가 raw에 넣는다        ≡    세일즈 담당이 판단해 Slack에 올린다
        │                              │
에이전트가 ingest          ≡    slack-collect가 가져온다
        │                              │
wiki로 정리                       ???  ← 여기만 다르다
```

**다른 점은 착지점 하나다.** 어제 안은 `vault/08-sales/`(wiki 층)로 바로 넣기로 했는데,
회의 `#6`대로면 **raw로 들어가서 ingest를 거쳐 wiki가 되어야** 한다.

**[수정 제안]**

```
  기존:  #sales 채널 ──▶ vault/08-sales/         (wiki에 직행)
  수정:  #sales 채널 ──▶ raw/slack/sales/  ──ingest──▶ wiki/sales/
```

Slack은 **투입구**이지 중심축이 아니다 — 사람이 직접 `raw/`에 파일을 놓아도
똑같이 동작해야 한다. 그러면 나중에 Slack을 안 써도 구조가 안 무너진다.

```

  ─────────                          ─────────
  1. B단계 (플러그인 제거)      →     1. schema 정의 (과제 1·2)
  2. 세일즈 채널 연동           →     2. lint L1~L4 구현 + 1회 실행
  3. 맥미니 이전                →     3. 3층 이사 (승인 시)
                                     4. ingest 입력 일반화
                                     ─────────────────────
                                     5. B단계 · 세일즈 · 맥미니 (연동층)
```

**단, B단계에는 구조와 무관한 운영상 급한 이유가 따로 있다.**

| | 사실 |
|---|---|
| 수집 | 2026-08-06 11:23 이후 멈춤 (6일째) |
| 원인 | `slack-sync` `autoSync: false` + 플러그인은 앱이 켜져 있어야만 동작 |
| 영향 | 구조를 아무리 잘 짜도 **raw에 새 자료가 안 들어온다** |

→ **[제안] B-0(토큰 이관)과 수집 재개만 먼저 떼어내 처리하고**, 나머지 B단계
(파일명 규칙·git-sync·다중 채널)는 구조 확정 후로 미룬다. raw가 비어 있으면
ingest를 정의해도 시험할 대상이 없다.
