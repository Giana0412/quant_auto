## 🔴 1. 숙제 3개 — 했는데 **절반만 했다**

> 이게 이번 미팅의 본론이다. 자책하려는 게 아니라 **무엇이 남았는지 정확히 짚기 위한 것**이다.

숙제를 하고 "완료"라고 보고하려 했는데, 카파시 원문을 읽고 대조해 보니
**층 구조는 맞췄지만 그 위에서 도는 동작을 절반만 만들었다.**

### 맞게 간 것

| 원문 | 우리 |
|---|---|
| Raw sources — *immutable, the LLM never modifies them* | ✅ `raw/` + lint L6 이 사후 수정 감시 |
| 3층 (raw / wiki / schema) | ✅ 5층으로 구현 (+index +log) |
| *The wiki is just a git repo of markdown* | ✅ |
| *Obsidian is the IDE; the LLM is the programmer* | ✅ |
| **폴더 역할이 스키마에 명시돼야** (32:04 지적) | ✅ [[폴더-규칙]] 등 7종 |

### 🔴 놓친 것 — 넷

**① ingest 가 기존 문서를 갱신하지 않는다**

> 원문: (…) **updates relevant entity and concept pages across the wiki** (…)
> **A single source might touch 10-15 wiki pages.**

```
카파시     새 자료 1개 → 10~15개 문서가 갱신됨   (누적)
우리       새 자료 1개 →  3개 문서가 새로 생김   (병렬)
```

**이게 *"왜 이렇게 링크가 적어요?"*(25:28) 의 답이다.** 167노드/530엣지가 나오는 이유는
매 ingest 마다 새 내용이 기존 페이지로 짜여 들어가기 때문이다. 우리는 고립된 3종 세트만 쌓인다.

**② 엔티티·개념 페이지가 아예 없다**

원문은 *entity pages, concept pages, comparisons, an overview, a synthesis* 를 말하는데
우리 `wiki/` 엔 **회의 기록과 설계 문서뿐**이다. *"채널A 와의 딜이 어떻게 됐지?"* 를
물으면 회의록 5개를 뒤져야 한다. ①과 같은 뿌리 — **갱신할 페이지가 없으니 ingest 가
갱신할 것도 없다.**

**③ lint 를 반대로 만들었다**

> 준범님(33:07): 린트는 **자동으로 정화가 돼야 돼요.** 연결되고 통합되고 통폐합되고,
> **이게 LLM 위키의 핵심이에요.**

나는 *"보고만 하고 고치지 않는다"* 로 만들었다. 원문의 lint 항목 6가지 중 우리가
하는 건 고아 페이지 하나뿐이다.

| 원문 항목 | 우리 |
|---|---|
| 문서 간 모순 · 낡은 주장 · 개념 누락 · 빠진 상호참조 · 데이터 공백 · 새 질문 제안 | ❌ |
| 고아 페이지 | ✅ |

나머지는 **의미를 봐야 해서 스크립트로 못 한다 — LLM 이 해야 한다.**
우리 L1~L7 이 쓸모없진 않지만(60건 잡아 고쳤다), **그건 문법 검사고 원문의 lint 는
건강 검진이다.** 이름을 같이 쓴 탓에 "lint 완료"로 보고한 것이 과했다.

**④ query 결과가 위키로 돌아오지 않는다**

> 원문: **good answers can be filed back into the wiki as new pages** (…)
> shouldn't disappear into chat history. This way your **explorations compound.**

`ask` 스킬을 읽기 전용으로 못박아 복리 고리를 끊어놨다.

### 근본 원인

**결정 14번("카파시 구조 채택")의 근거 문서를 읽지 않고 자체 설계했다.**
원문이 vault 에 없었다 — 어제 넣었다([[karpathy-llm-wiki]]).

준범님이 *"그게 다 나와 있어요"*(34:38) 라고 한 게 이 문서다.

### 8/12 저녁에 고친 것 (작고 명확한 것만)

| | 무엇 | 검증 |
|---|---|---|
| schema 를 에이전트가 로드하게 | 레포 루트 `CLAUDE.md` 신설 | 파일 읽기 없이 규칙을 답하는 것 확인 |
| log 를 append-only 로 | 원문 형식 `## [날짜] op \| 대상` | `grep -c` 로 **조회 횟수가 세어짐** |
| index 에 한 줄 요약 | 63/63 부착 | |

**①②③④ 는 위키의 성격을 바꾸는 일이라 손대지 않았다** — *"구조 같은 거는 제가 나중에
잡으면 되니까"*(34:04) 라고 하셨으므로.

## 3. 헤르메스가 vault 를 읽는 경로 [제안]

결정 13번(**옵시디언=메모리 / 헤르메스=CPU**)이 성립하려면 헤르메스가 메모리를
읽어야 하는데 지금은 못 읽는다.

| | 방법 | 평가 |
|---|---|---|
| **A** | 헤르메스 컨테이너가 **repo 를 clone** | ✅ **권함** — research 가 이미 쓰는 패턴(`com.oao.research-pull`), 서버가 안 는다 |
| B | vault 를 MCP 서버로 노출 | 모델 중립이나 "서버 없음" 원칙과 충돌 |
| C | 헤르메스가 `ask` 스킬 호출 | Claude Code 의존 → 260811 핵심논의 2 와 충돌 |

**합의 전이라 구현은 멈춰뒀다.**

## 4. 슬랙 인입 경로 — 방향은 동의합니다

> 준범님(42:03, 46:28): 이거 **왜 굳이** 슬랙이랑 옵시디언이랑 플러그인이랑 CLI 를
> 거쳐서 하는 거죠 (…) **데이터의 인입점은 오르카랑 클로드가 돼야 되는 거죠**

동의한다. 다만 사실관계를 하나 적어둔다 — **그 경로가 8/6 부터 6일간 죽어 있었고
8/12 에 되살렸다.** 8/10 주간회의 전사본이 유실될 뻔한 걸 복구했다.

즉 **없앨 길을 포장한 셈**인데, 당장 회의록이 안 들어오는 상태를 두고 갈 수는 없었다.
인입점을 오르카+클로드로 옮기는 건 §1-① 과 같이 가야 하는 일이라 합의 후 진행이 맞다고 본다.
