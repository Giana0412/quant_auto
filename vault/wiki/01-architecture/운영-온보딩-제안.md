# 운영·온보딩 제안

> **전제**: 설계·구조는 [[이준범]] 안(`oursymbol/oao-wiki`)으로 확정. 이 문서는 그 위에
> **"어떻게 굴릴 것인가"** 만 다룬다. 구조를 다시 논하지 않는다.
> **일정**: 8/19(수) 전사 온보딩

---

## 0. 결론 먼저

**1. 위키는 정보가 없어서 죽지 않는다. 안 쓰여서 죽는다.** 조사한 실패 사례가 전부 같은
말을 한다(§1). 그리고 **우리는 이미 그 상태다** — 준범님 lint 기록에 `query 소비 0건`.

**2. 🔴 그런데 우리에겐 대부분의 위키에 없는 이점이 하나 있다.** 열람을 질문으로 하게
설계돼 있어서 **"읽혔는지"가 로그에 남는다**(§2). 남의 위키는 이걸 못 잰다.

**3. 실패한 질문이 곧 다음 할 일이다.** *"위키에 없다"* 로 끝난 질문을 모으면 그게
ingest 백로그다(§2-2). 정직한 거부를 규칙으로 넣어둔 덕에 **공짜로 생기는 자산**이다.

**4. 온보딩은 설명이 아니라 손으로 시켜야 한다.** 능동 학습은 1개월 뒤 **93.5%** 를
기억하고 수동 학습은 **79%** 다(§4). 수요일에 데모만 보여주면 목요일에 아무도 안 쓴다.

**5. 강제는 규칙이 아니라 구조로 건다.** GitLab 은 슬랙을 90일만 보관해서 문서화를
강제한다(§3). 우리 버전을 하나 정해야 한다.

## 1. 위키가 죽는 이유 — 조사 결과

여러 실패 보고가 **같은 네 가지**로 수렴한다.

| 실패 모드 | 원문 |
|---|---|
| **저장 문제로 착각** | *"내부 위키는 문서화를 **지식 관리 문제가 아니라 저장 문제로** 다루기 때문에 실패한다. 페이지를 더 넣고 기여자를 더 늘려도 안 고쳐지는 구조적 문제다."* |
| **콘텐츠 부패** | *"문서된 진실과 운영 현실의 간극이 **조용히, 계속** 벌어진다. 프로세스 변경·도구 이전·조직 개편마다 위키의 일부가 조용히 틀린 것이 된다."* |
| 🔴 **신뢰 붕괴** | *"지표상으로는 위키가 잘 돌아가는 것처럼 보였지만, **사람들이 콘텐츠를 찾아도 그게 진짜인지 알 방법이 없었다.** 정리된 지식과 나머지를 구분할 방법이 부족했다."* |
| **참여 없음** | *"위키가 쉽게 고칠 수 있게 만들어졌는데도, 직원 전원이 위키를 최신으로 유지하는 데 적극적인 직장은 드물다."* |

> **세 번째가 제일 무섭다.** 문서가 많아지는데 믿을 수 없으면 **아무도 안 본다.**
> 그리고 그건 지표(페이지 수·문서 수)로는 안 잡힌다.

### 우리에게 해당하는가

| | 상태 |
|---|---|
| 저장 문제로 착각 | ⚠️ 지금까지 논의가 **거의 다 "어떻게 넣나"** 였다 (준범님 지적과 같음) |
| 콘텐츠 부패 | ⚠️ lint 항목에 "낡은 주장" 있음. 다만 **주 1회 사람 트리거** |
| 🔴 **신뢰 붕괴** | 🔴 **막을 장치가 없다.** 확정된 결정과 초안이 같은 무게로 놓인다 (§5-3) |
| 참여 없음 | 🔴 **query 0건.** 이미 시작됐다 |

## 2. 🔴 우리만 가진 이점 — 읽힘을 측정할 수 있다

일반적인 위키는 **읽힘을 못 잰다.** 조사에서도 이렇게 나온다.

> *"조회수·이탈률·체류시간을 주요 지표로 쓰면 **일관되게 틀린 결론**이 나온다.
> 사용자 결과와 연결되지 않기 때문이다."*

**그런데 우리 설계는 다르다.** CLAUDE.md 제1 운영원칙:

> *"열람도 기본적으로 질문(query)으로 한다 — **그래야 활용이 log 에 남는다.**"*

**이건 설계된 이점이다.** 질문이 로그에 한 줄씩 쌓이므로,

```bash
grep -rh "^## \[.*\] query" log/ | wc -l     # 얼마나 쓰이나
grep -rh "^## \[.*\] ingest" log/ | wc -l    # 얼마나 들어오나
```

**이 둘의 비율이 위키가 살아 있는지를 말해준다.** 지금은 `ingest 다수 : query 0` 이다.
창고는 채워지는데 아무도 안 꺼내 간다.

### 2-2. 실패한 질문 = 다음 주 할 일

CLAUDE.md query 규칙에 **정직한 거부**가 이미 들어 있다.

> *"위키·raw 어디에도 근거가 없으면 **'위키에 없다'고 답한다** — 추측으로 빈칸을 채우지 않는다."*

조사에서도 **실패한 검색이 핵심 지표**로 꼽힌다.

> *"결과가 없는 검색(failed searches)의 수는 유용한 지식베이스 지표다."*

**두 개를 붙이면 백로그가 공짜로 생긴다.**

```
질문 → "위키에 없다" → 로그에 남음 → 주간 정리 때 모음 → 다음 ingest 대상
```

> **제안**: 거부 로그에 표시를 하나 붙인다. `query · 김규형 | 질문 요지 → ❌없음`
> 주 1회 `grep '❌없음'` 하면 **"팀이 알고 싶어 했는데 없던 것"** 목록이 그대로 나온다.
> 이건 우리가 만들 게 거의 없다 — **로그 형식에 표시 하나 추가**면 된다.

## 3. 강제 장치 — 규칙이 아니라 구조로

GitLab 의 핸드북 퍼스트가 유지되는 이유는 착한 사람이 많아서가 아니다.

> 🔴 *"**제한적 보존 정책이 강제 장치(forcing function)로 작동한다.**"*
> — 슬랙 활동을 **90일만** 보관한다. 채팅 이력에 의존하지 말고 문서로 가라는 압력.
>
> *"**해결책을 먼저 문서화하고, 그 다음에** 슬랙·이메일로 알린다"* — 순서를 뒤집는다.
> *"핸드북에서 먼저 찾아보고" 동료에게 묻는다.*

PostHog 도 같은 방향이다.

> *"우리는 **슬랙 메시지보다 이슈를 선호한다** — 공개돼 있고 코드 워크플로와 이어지니까."*
> *"공지는 슬랙 채널로 — **방해받지 않고 일하도록.**"*
> *"'하겠습니다', '알겠습니다', '할 일 목록에 있습니다' 같은 답은 **도움이 안 된다**"* —
> 기한을 말하거나 이미 했다고 말할 것.

### 우리 버전 — 세 개 중 고른다

| 안 | 무엇 | 비용 | 세기 |
|---|---|---|---|
| **A. 링크로 답하기** | 슬랙에서 질문에 답할 때 **위키 링크를 붙여서** 답한다. 링크가 없으면 = 위키에 없다는 뜻 → 그 자리에서 ingest 대상 | **0** | 중 |
| **B. 회의 안건을 링크로** | 안건을 위키 페이지 링크로 낸다. 없으면 만들어야 함 | 0 | 강 |
| **C. 슬랙 보존 단축** | GitLab 방식 그대로 | 플랜·합의 필요 | 매우 강 |

> **A 를 권한다.** 비용이 0 이고, **읽기 압력과 쓰기 압력이 동시에** 걸린다.
> 답하는 사람은 위키를 찾아봐야 하고(읽기), 없으면 넣어야 한다(쓰기).
> C 는 우리 규모에 과하고 반발이 크다.

## 4. 온보딩 (8/19 수)

### 4-1. 설명하지 말고 시킨다 — 근거

> **능동 학습자는 1개월 뒤 93.5% 를 기억하고, 수동 학습자는 79% 다.**
> *"교육 중에 직접 해본 작업은 나중에 기억할 확률이 높다."*
> *"기능 전체 투어가 아니라 **첫 가치까지의 경로**에 집중하라."*

**데모만 보면 목요일에 아무도 안 쓴다.** 온보딩 자리에서 각자 **자기 손으로 한 번씩**
돌려봐야 한다.

### 4-2. GitLab 의 장치를 번역한다

> 🔴 GitLab: *"**입사 첫 주에 모든 팀원이 머지 리퀘스트를 하나 낸다. 코딩을 해본 적
> 없는 사람도.**"* 온보딩 과제 중 하나가 *"핸드북을 개선하라"* 인데, 목적이 둘이다 —
> MR 을 한 번 더 내보게 하는 것, 그리고 **핸드북을 직접 돌아다니게 하는 것.**

**그대로는 못 옮긴다.** 우리 제1원칙은 *"모든 문서는 LLM 에이전트를 통해서만 생성·수정"*
이라 사람이 MR 을 내지 않는다. **우리 대응물은 이것이다.**

```
GitLab 의 "첫 주에 MR 하나"   →   우리의 "첫 주에 소스 하나 + 질문 하나"
```

| | 무엇 | 왜 |
|---|---|---|
| **① 소스 하나 넣기** | 자기가 가진 회의록·자료 하나를 ingest | 넣는 경로를 몸으로 안다. **로그에 자기 이름이 남는다** |
| **② 질문 하나 하기** | 위키에 대고 아무거나 물어본다 | 꺼내는 경로를 안다. **query 0건을 깬다** |

**둘 다 로그에 남으므로 온보딩 완료 여부가 자동으로 측정된다.**

> AI 도입 조사에서도 같은 기준이 나온다 — *"**75일차까지 전원이 계정을 갖고 최소 한 개
> 작업을 AI 로 완료**해야 한다. 아직 안 쓰는 사람이 있으면 **왜 안 쓰는지 알아낸다.**"*
> *"강제하는 것보다 **왜 안 쓰는지 찾아내는 게 더 중요하다.**"*

### 4-3. 수요일 세션 구성 (60분안)

| | 시간 | 무엇 | 왜 |
|---|---|---|---|
| 1 | 10분 | **왜 만드나** — "묻는 게 사람에서 위키로 바뀐다" | 개념. 짧게 |
| 2 | 10분 | **실제 질문 3개 시연** — 우리 위키에 답이 있는 것으로 | 첫 가치를 눈으로 |
| 3 | **20분** | 🔴 **각자 자기 질문 하나씩 직접** | **여기가 핵심.** 손으로 안 하면 안 남는다 |
| 4 | 10분 | **소스 넣기 1회 실습** | 넣는 경로 |
| 5 | 10분 | 규칙 3개 + 이번 주 과제 | 짧게. 문서로 남기고 말로는 3개만 |

> **3번에서 "위키에 없다"가 나오는 게 정상이고 오히려 좋다.** 그 자리에서
> *"이게 백로그가 되는 겁니다"* 를 보여주면 §2-2 가 개념이 아니라 경험이 된다.
> **실패를 숨기지 말고 설계의 일부로 보여준다.**

### 4-4. 말하지 말아야 할 것

| | 왜 |
|---|---|
| 남의 회사 숫자를 우리 성과처럼 | Clearwater "온보딩 몇 주→몇 시간"은 **남의 숫자**다. *"이런 사례가 있다"* 까지만 |
| 아직 없는 기능 시연 | 데일리·캘린더 연동은 **없다.** 시연하면 그 자리에서 들킨다 |
| "다 자동으로 됩니다" | 넣는 건 사람이 판단해서 넣는다. 과장하면 첫 실패에 신뢰가 깨진다 |

## 5. 운영 리듬

### 5-1. 주간 — 사서(정원사) 1명, 돌아가며

> *"공유 책임은 **주도하는 사람이 없으면 3분기쯤엔 선택사항이 된다.**"*
> 위키 정원사의 일: 죽은 링크 수리 · **필요한 곳에 링크 생성** · 승인이 오래 밀린 것 추적 ·
> 페이지를 최신·정돈 상태로 유지

준범님 안건 7번 *"에이전트를 통한 린트 관리(사서 역할)"* 가 여기다. **다만 사람이 한 명은
붙어야 한다** — lint 는 준범님 설계상 주 1회 **사람 트리거**다.

| 주 1회 (15분) | 무엇 |
|---|---|
| 1 | lint 돌리고 결과 확인 |
| 2 | 🔴 **거부된 질문(❌없음) 모아서 ingest 백로그로** |
| 3 | 미처리 소스(raw 인데 참조 0) 처리 |
| 4 | 로그에 `lint · <행위자>` 남기기 |

**돌아가면서 맡는다.** 한 사람이 계속하면 그 사람만 위키를 알게 된다.

### 5-2. 월 1회 — 쇼앤텔

> AI 도입 조사: *"직원들이 AI 를 쓰는 창의적인 방법을 공유하는 **월간 '쇼앤텔'** 세션이
> 모범 사례를 유기적으로 퍼뜨린다."*
> *"**공용 프롬프트 라이브러리** — 특정 작업에 잘 먹히는 검증된 프롬프트 모음."*

30분이면 된다. *"이번 달에 이렇게 물어봤더니 이게 나왔다"* 를 각자 하나씩.

> **잘 먹힌 질문은 위키에 저장한다.** CLAUDE.md query 규칙 3번에 이미 있다 —
> *"재사용 가치 있는 답변은 해당 서가에 페이지로 저장."* Karpathy 원문도 같다 —
> *"좋은 답변은 **위키에 새 페이지로 되돌려 넣을 수 있다.**"* 쇼앤텔이 그 수집 자리다.

### 5-3. 🔴 신뢰 등급 — §1 의 세 번째 실패를 막는 유일한 장치

**Clearwater**(실제 회사 엔지니어링 팀, API 1,200개)는 층을 **"얼마나 믿을 수 있나"** 로 나눈다.

```
Tier 1  리더십 승인      🔴 AI 에이전트에게 읽기 전용
Tier 2  기술 기반·설계
Tier 3  스프린트·회의록
Tier 4  Archive          낡은 것. 지우지 않고 내린다
```

**우리 구조(000~900)는 "무엇에 관한가"로만 나뉜다.** 확정된 결정과 한 번 언급된 아이디어가
같은 무게로 놓인다. §1 의 *"찾아도 진짜인지 알 방법이 없다"* 가 정확히 이 상태다.

> **제안 (가장 가벼운 형태)**: 서가를 늘리지 말고 **frontmatter 에 한 줄** 넣는다.
>
> ```yaml
> confidence: confirmed | draft | superseded
> ```
>
> - `confirmed` — 회의에서 확정됐거나 리더 승인
> - `draft` — 제안·검토 중
> - `superseded` — 낡음. **지우지 않고 내린다** (Clearwater Tier 4)
>
> query 답변이 이 값을 같이 말해주면 *"이건 아직 제안입니다"* 가 자동으로 붙는다.
> 낡은 것을 지우지 않는 이유는 **"왜 그렇게 정했는지"가 거기 남기 때문**이다.

## 6. 역할 — 챔피언

> *"AI 성공은 **70% 가 사람과 프로세스**이지 알고리즘이 아니다."*
> *"AI 롤아웃은 기술보다 **사람·문화에서 4배 더 자주** 멈춘다."*
> 🔴 *"**자기 일에서 눈에 보이게 AI 를 쓰는 챔피언**이, 추상적으로 AI 를 가르치는 외부
> 트레이너보다 효과적이다."* / *"챔피언이 도입 곡선 속도를 **2배로** 만들었다."*

**챔피언은 가르치는 사람이 아니라 눈에 보이게 쓰는 사람이다.**

| | 누가 | 무엇 |
|---|---|---|
| 아키텍트 | 이준범 | 구조·스키마 정본 |
| **운영 챔피언** | 김규형 | 슬랙 질문에 **위키 링크로 답하기**를 눈에 보이게. 백로그 관리 |
| 주간 사서 | 돌아가며 | §5-1 |

> 🔴 **가장 실질적인 것**: 슬랙에서 누가 물으면 **답을 위키 링크로 준다.**
> 이게 §3-A 강제 장치이자 챔피언 행동이자 데모다. **하나로 셋을 한다.**

## 8. 측정 — 무엇을 보고 살았다/죽었다 하나

**조회수는 안 쓴다** (§2 — *"일관되게 틀린 결론"*).

| 지표 | 어떻게 | 목표 |
|---|---|---|
| 🔴 **주간 query 수** | `grep -rh "query" log/` | **사람 수 이상 / 주** |
| 🔴 **거부율** | `❌없음` 비율 | 초기엔 높은 게 정상. **줄어드는 추세**가 중요 |
| **기여자 수** | `git log --format='%an' \| sort -u` | 4주 내 **전원 1회 이상** |
| **미처리 소스** | lint 항목 (이미 있음) | 주 단위로 0 수렴 |

> **query : ingest 비율이 핵심이다.** 지금은 `다수 : 0` 이다.
> **1:1 을 넘으면 창고가 아니라 도구가 된 것이다.**

## 9. 안 되면 어디서 깨지나 — 정직하게

| | 위험 |
|---|---|
| 🔴 **첫 2주에 query 가 안 붙으면** | 그대로 끝난다. §1 의 "참여 없음" 경로. **온보딩 과제 ②가 이걸 막는 유일한 장치** |
| **"위키에 없다"를 몇 번 겪으면** | 사람들이 안 묻게 된다. 그래서 **초기 거부율이 높을 거라고 미리 말해야** 한다 |
| **직접 편집이 늘면** | 제1원칙은 lint 사후 복원뿐이다. 착지 게이트가 없다 |
| **사서가 고정되면** | 그 사람만 위키를 알게 된다. 당번제가 필요한 이유 |
| **팀이 15명 넘으면** | *"규범은 서로 완전히 신뢰하는 **몇 명까지만** 확장된다"* — 지금 6~7명 |
