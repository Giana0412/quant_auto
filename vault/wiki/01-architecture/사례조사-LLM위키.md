>

## 0. 38건 조사해서 알게 된 것, 다섯 줄

1. **스킬 개수가 자릿수로 다르다.** 우리 4개, 많은 곳은 26개·MCP 도구 40+ (§2).
2. **"Obsidian 앱 런타임 의존은 안 된다"는 이미 업계 결론**이다 (§3).
   이준범 지적과 정확히 같다.
3. 🔴 **실시간은 포기 안 해도 된다.** "앱 상주 아니면 실시간 포기"는 틀린 이분법이었다.
   병목은 *"남의 기기가 새 커밋을 알아채는"* 구간 하나뿐이고, `git ls-remote` 실측
   **671ms** — **30초 폴링이면 평균 15초 지연, 앱 불필요, git 병합 유지** (§5-7).
   **단, 그 폴링 데몬이 아직 없다.** 확인해보니 지금 싱크는 전부 obsidian-git
   플러그인(10분, **앱 켜져 있을 때만**)이 하고 있었다 — 만들어야 할 게 남았다.
4. **"결정이 바뀐다" 문제에 정면 해법이 있다** — Zep 의 **양시간 무효화**.
   지우지 않고 유효 기간을 닫는다 (§5-8). 우리 결정사항이 계속 쌓이기만 하는 문제의 답.
5. 🔴 **우리가 만들려는 것의 제품판이 이미 있다** — Basic Memory(MCP)와 **Tana**.
   *"왜 갖다 쓰지 않고 직접 만드나"* 에 답할 수 있어야 한다 (§5-9).

> **가장 불편한 발견은 5번이다.** Tana 는 *"회의를 타입 있는 연결 항목으로 자동
> 변환하고, 권한 걸린 팀 맥락으로 공유하고, MCP 로 외부 에이전트에 답한다."*
> 우리가 만들려는 것과 거의 같다.

## 5. 🔴 Obsidian 을 쓰지 말아야 할 이유 — 조사 결과

> 이준범(260813, 53:51): **옵시디언을 쓰면 안 되는 이유가 있을 수도 있잖아요.**
> 도입하지 않아야 되는 이유가 있다면 그게 뭔지를 고민해 봐달라고 한 적이 있었을 거예요.

[LeafWiki 의 반박](https://leafwiki.com/blog/obsidian-is-not-a-team-wiki/) 이 이 질문에 정면으로 답한다. **우리 상황에 그대로 걸린다.**

| 지적 | 우리 상황 |
|---|---|
| *"새 사람마다 Git 이 필요하고, 클론해야 하고, Obsidian 을 깔아 폴더를 지정해야 한다. **글 한 줄 쓰기 전에 세 단계**"* | 🔴 그대로 해당. 설계문서 §12-5 의 온보딩 문제 |
| *"두 사람이 같은 파일을 동시에 고치면 마크다운 머지 충돌이 난다. **팀 대부분은 그걸 풀 능력이 없다**"* | 🟡 `resolve-conflict` 스킬로 완화. 근본 해결은 아님 |
| *"'그 페이지 링크 좀 보내줘' 하면 답이 GitHub URL 이다. **브라우저에서 열어 고칠 수 있는 페이지가 아니다**"* | 🔴 그대로 해당. 지금 이준범에게 파일을 첨부해 보내고 있다 |
| *"Obsidian Sync 는 기기 동기화지, **역할·접근제어·브라우저 인터페이스가 있는 공유 워크스페이스가 아니다**"* | 🔴 그대로 해당 |

**인정할 것**: 같은 글이 Obsidian 의 강점도 명시한다 — 로컬 우선, 플러그인 생태계,
그래프 뷰, **락인 없는 평문 마크다운**.

**따라서 판단은 이렇게 갈린다.**

```
"팀 위키" 로 쓰려면          → Obsidian 은 나쁜 선택이다 (위 4가지)
"LLM 의 작업 공간" 으로 쓰려면 → 평문 마크다운 + git 이 오히려 강점이다
```

이준범의 입장(*"직원들에게 옵시디언 세팅을 시킬 것 같지 않다"*)은 **후자**다.
사람은 Orca·Claude 로 접근하고, Obsidian 은 안 깔아도 된다. 그러면 위 4가지 중
1·3·4 가 상당 부분 무력화된다 — **애초에 사람이 Obsidian 을 안 쓰니까.**

> 이게 우리가 답해야 할 "철학"의 실체로 보인다.

## 5-7. 🔴 실시간 싱크 — 포기 안 해도 된다 (실측 포함)

§4 에서 *"아무도 못 풀었다"* 고 썼는데, **한 곳은 풀었다.**

### Obsidian LiveSync (자체 호스팅 CouchDB)

> **무료 중 유일하게** 실시간 싱크 + **청크 단위 충돌 병합** + iOS 지원 +
> 완전 자체 호스팅을 동시에 주는 선택지.

작동 원리가 영리하다. **각 기기 안에 PouchDB 를 넣고 서버에 CouchDB 를 둔다.**
둘은 같은 복제 프로토콜을 쓰므로 **싱크가 곧 DB 복제**가 된다. 기기를 떠나기 전에
종단간 암호화한다. 백엔드는 CouchDB · S3 호환(MinIO·R2) · **WebRTC P2P** 중 선택.

**그런데 우리 조건과 정면으로 부딪힌다.**

```
LiveSync 는 Obsidian 플러그인이다  →  Obsidian 이 떠 있어야 돈다
이준범: "직원들한테 옵시디언 세팅을 시킬 것 같지는 않다" (0813, 29:17)
```

즉 **실시간을 얻으려면 전원이 Obsidian 을 켜 두어야 한다.** 우리가 피하려던 바로 그것이다.
공식 경고도 있다 — *"다른 동기화 솔루션과 같이 켜지 말 것"*, *"진행 표시가 사라지기 전에
Obsidian 을 닫지 말 것"* (특히 삭제 후 손상 위험).

### 🔴 그런데 "셋 중 하나"라는 프레임 자체가 틀렸다

처음엔 이렇게 정리했다 — ① LiveSync(실시간, 앱 상주) ② git+launchd(앱 없음, **실시간 포기**)
③ Obsidian Sync 구매. 더 파보니 **②의 "실시간 포기"가 사실이 아니다.**

실시간을 한 덩어리로 보면 안 된다. **구간을 나눠야 답이 나온다.**

```
내가 저장  ──A──▶  내 기기가 올림  ──B──▶  서버  ──C──▶  남의 기기가 받음  ──▶ 남이 봄
           (감지)                                    (알아채기)
```

**병목은 A 도 B 도 아니고 C 다.** A(파일 변경 감지)는 OS 가 즉시 알려주고(fsevents/inotify),
B(업로드)는 1초 미만이다. 문제는 **"남의 기기가 새 커밋이 생긴 걸 어떻게 아느냐"** 뿐이다.
그리고 C 는 Obsidian 과 아무 상관이 없다.

### 구간 C 를 푸는 방법 — 실측

C 를 푸는 길은 둘이다. **물어보거나(폴링), 알려주거나(푸시).**

폴링 비용을 실제로 쟀다. 이 레포(.git 24MB, 122파일)에서 `git ls-remote` —
객체는 안 받고 "원격 해시가 뭐냐"만 묻는 명령 — 를 5회 실행한 결과다.

| 폴링 주기 | 하루 실행 | 하루 총 소요 | **평균 지연** |
|---|---|---|---|
| 30초 | 2,880회 | **32분** | **15초** |
| 1분 | 1,440회 | 16분 | 30초 |
| 5분 | 288회 | 3분 | 2분 30초 |
| 10분 | 144회 | 2분 | 5분 |

> 실측: `ls-remote` 평균 **671ms**, `fetch`(변경 없을 때) 평균 749ms. 대부분 네트워크
> 왕복이고 CPU 는 거의 안 쓴다. GitHub API 호출 제한과도 무관하다 — git 프로토콜이라
> REST 쿼터를 안 먹는다.

**30초 폴링이면 평균 15초 안에 남의 화면에 뜬다.** 그 대가는 노트북 한 대당 하루
32분의 백그라운드 대기(그것도 대부분 네트워크 응답 기다리는 시간)뿐이다.

### ⚠️ 그럼 지금 우리는 어떤 상태인가 — 확인해보니 생각보다 나빴다

처음엔 *"launchd 주기 3600 을 30 으로 바꾸면 끝"* 이라고 썼다. **확인해보니 틀렸다.**
실제로 코드와 설정을 열어본 결과다.

| 확인한 것 | 결과 |
|---|---|
| `com.giana.obsidian-slack-docs-sync.plist` `StartInterval` | **3600** |
| 그 잡이 git 을 건드리나 | 🔴 **아니다.** 스크립트에 *"git commit/push는 하지 않는다"* 고 명시 |
| `.automation/` 안에 `git pull`·`fetch` 가 있나 | 🔴 **하나도 없다** |
| 그럼 누가 당겨오나 | `vault/.obsidian/plugins/obsidian-git` — `autoPullInterval: **10**`(분) |

**즉 지금 우리 팀 싱크는 100% Obsidian 플러그인이 하고 있다.**

```
Obsidian 켜져 있음  →  10분마다 pull
Obsidian 꺼져 있음  →  🔴 아무 일도 안 일어난다
```

3600초 잡은 **수집·정리 파이프라인**이지 싱크가 아니었다. 두 개를 섞어 본 게 실수였다.

> **바로잡은 결론.** 15초 지연을 얻으려면 **한 줄 수정이 아니라 새 launchd 잡 하나를
> 만들어야 한다** — 30초마다 `ls-remote` 해서 해시가 다르면 `pull` 하는 것. 20줄쯤이다.
> 아키텍처를 바꾸는 일은 아니지만 **없던 걸 만드는 일**은 맞다.
> 이게 그동안 미뤄둔 **B-2(앱 독립 git 싱크)** 이고, 아직 착수 안 했다.
>
> 그리고 이건 실시간 이전에 **더 근본적인 문제**를 드러낸다 —
> *"직원은 Obsidian 을 안 쓴다"* 고 전제해 놓고, **정작 싱크를 Obsidian 플러그인에
> 맡겨 두었다.** 앱을 안 쓰는 사람은 지금 구조에서 파일을 아예 못 받는다.

### 이미 만들어져 있는 도구들 (구간 A+C 자동화)

직접 짤 필요도 없다. 다만 **셋 다 결함이 있다** — 이게 조사의 결론이다.

| 도구 | A(내 변경) | C(남의 변경) | 충돌 | 앱 필요? |
|---|---|---|---|---|
| **git-auto-sync** (GitJournal) | 파일시스템 감시 | **10분 폴링** + 절전 해제 시 | 🔴 **rebase 전용. 충돌 나면 그 레포 싱크를 중단**하고 알림만 | ❌ 불필요 (데몬) |
| **gitwatch** | `inotifywait` 즉시 | ❌ **없음** (푸시 전용) | 다루지 않음 | ❌ 불필요 |
| **Syncthing** | 즉시 | 즉시 (P2P) | 🔴 **파일 단위 최신것 우선** — 진 쪽은 `.sync-conflict-<날짜>-<기기>.md` 로 개명 | ❌ 불필요 (데몬) |

**Syncthing 의 충돌 규칙을 정확히 알아야 한다.** 수정 시각이 늦은 파일이 원래
이름을 갖고, 이른 쪽이 개명된다(시각이 같으면 기기 ID 가 큰 쪽이 개명). 데이터가
사라지진 않지만 **줄 단위 병합이 없다.** 두 사람이 같은 회의록의 다른 문단을 고치면
git 은 둘 다 살리지만 **Syncthing 은 한 명 것을 통째로 옆 파일로 밀어낸다.**
그리고 그 충돌 파일은 전 기기로 다시 퍼진다.

→ **문서 저장소에는 git 의 줄 단위 병합이 맞다.** Syncthing 은 속도는 이기지만
협업 편집에서 진다.

### 푸시(웹훅)는 왜 접었나

GitHub 웹훅으로 알리면 지연 0에 가깝다. 그런데 **웹훅을 받으려면 각자 노트북에
공개 주소가 있어야 한다.** Cloudflare Tunnel·ngrok·Tailscale Funnel 같은 터널을
1인당 하나씩 띄워야 하고, 그건 "직원은 설치 안 한다"는 전제와 정면으로 부딪힌다.
**15초를 0초로 줄이자고 1인당 터널을 세우는 건 수지가 안 맞는다.**

### CRDT(Yjs·Automerge)는 우리 문제가 아니다

"충돌 없는 편집"으로 CRDT 가 자주 거론된다. 조사 결과 **적용 대상이 다르다.**
Yjs·Automerge 는 **에디터에 붙는 라이브러리**다 — 같은 문서를 동시에 타이핑하는
구글독스형 상황을 푼다. 우리는 **각자 다른 시각에 다른 파일을 고치는** 상황이고,
저장 단위가 일반 마크다운 파일이다. CRDT 를 쓰려면 에디터를 새로 만들어야 한다.
(Milkdown 처럼 Yjs 를 붙인 마크다운 에디터가 있긴 하나 Obsidian 이 아니다.)

### 🔴 정리 — 실제 선택지

| | 지연 | Obsidian 필요 | 줄 단위 병합 | 비용 |
|---|---|---|---|---|
| 현재 (git + launchd 1시간) | **최대 1시간** | ❌ | ✅ | 0 |
| **git + launchd 30초** | **평균 15초** | ❌ | ✅ | 0 |
| git-auto-sync 데몬 | 평균 5분 | ❌ | ⚠️ 충돌 시 싱크 중단 | 0 |
| Syncthing | 즉시 | ❌ | 🔴 파일 단위 덮어쓰기 | 0 |
| Obsidian LiveSync | 즉시 | 🔴 **전원 상주** | ✅ 청크 병합 | 서버 운영 |
| Obsidian Sync | 즉시 | 🔴 전원 설치 | ✅ | 유료·20명 한도 |

**가야 할 곳은 2행이다.** 앱도 필요 없고, git 의 줄 단위 병합도 유지하고, 지연은 15초다.
**우리는 지금 1행에도 못 있고 그 아래에 있다** — 앱이 꺼지면 0이니까.

> **준범님 기준으로 답하면** (0813, 43:38 —
> *"내가 회의록을 올리고 다른 사람이 그 회의록을 볼 때까지의 전 과정을 막힘없이
> 설명할 수 있어야 돼요. 이게 운영이에요."*)
>
> **지금 (사실):**
> ① 내가 Orca 에 전사본을 넣는다 → ② 에이전트가 3종 문서를 만든다 → ③ **내가 Obsidian 을
> 켜 두었다면** 10분 안에 커밋·푸시된다 → ④ **남도 Obsidian 을 켜 두었다면** 10분 안에
> 받는다 → ⑤ 🔴 **둘 중 하나라도 꺼져 있으면 전달이 안 된다.**
> → 지금은 이 문장에서 *"막힘없이"* 가 안 된다. 막히는 지점이 ③④에 있다.
>
> **B-2 를 만든 뒤 (목표):**
> ① 넣는다 → ② 만든다 → ③ 데몬이 push(1초 미만) → ④ 남의 기기 데몬이 30초마다
> 원격 해시 확인(**671ms 실측**) → ⑤ 다르면 pull → ⑥ **평균 15초 뒤 남의 폴더에 있다.**
> 앱을 켰는지는 무관하다 — 켤 때 이미 거기 있다.

**그리고 지연을 풀어도 충돌이 남는다.** 두 사람이 같은 문서를 동시에 고쳤을 때 누가
어떻게 푸느냐 — `resolve-conflict` 스킬의 몫인데 **아직 실전 검증을 못 했다.**
위 표에서 Syncthing 을 떨어뜨린 이유가 바로 이것이므로, git 을 고른 값을 하려면
이 스킬이 실제로 동작해야 한다.

## 5-8. 🔴 "결정이 바뀐다" 문제 — Zep 의 양시간 그래프

§5-2 의 비판(*"바뀌는 기한·틀어진 계획을 위키는 못 따라간다"*)에 대한 **정면 해법**이 있다.

> **시간 지식 그래프**란 모든 사실이 시간을 지닌 그래프다 — **언제 참이 되었고,
> 언제 참이 아니게 되었고, 출처가 어디인지.** 그래서 무엇이 알려져 있는지뿐 아니라
> **그 앎이 어떻게 변해왔는지**를 표현한다.

**핵심 기법 — 지우지 않고 무효화한다**

> 새 정보가 기존 사실과 모순되면 그 엣지를 **삭제하지 않고 `t_invalid` 타임스탬프를
> 적어 무효화**한다. 그래서 그래프는 **"언제 무엇을 믿고 있었는가"** 에 답할 수 있고,
> **낡은 사실을 현재로 내주는 일이 없다.**

**양시간(bi-temporal)** — 사실마다 두 시간선을 둔다: **실제로 참이었던 기간**과
**우리가 그것을 알게 된 시점.** 소급 정정도 다룰 수 있다.

**우리 문제에 그대로 대응된다.**

| 우리 상황 | Zep 방식이라면 |
|---|---|
| 260728 결정 6번(3주 일정) vs 260811 "구조 먼저" — **둘 다 유효한 것처럼 남아 있다** | 앞 결정의 유효 기간이 닫히고 뒤 결정이 열린다 |
| 8/11 "공용 계정 1개" → 8/13 "각자 계정" | 덮어쓰지 않고 **바뀐 이력이 남는다** |
| `할일` 70건에 **이미 끝난 것이 섞여 있다** | 완료 시점에 유효 기간이 닫힌다 |

> **지금 우리 결정사항 문서는 계속 쌓이기만 한다.** 무엇이 아직 유효한지 판단하려면
> 사람이 날짜를 비교해야 한다. [[query-규칙]] 에 *"날짜를 비교해 최신을 우선하되
> 바뀌었다는 사실 자체를 알린다"* 고 적어뒀는데, 그건 **규칙으로 때운 것**이지
> 구조로 푼 게 아니다.

| | Basic Memory | 우리 |
|---|---|---|

> 준범님의 *"자체 MCP 를 쓸 수 있는 스킬들을 만들어 놓고"*(0811, 10:34) 와도 맞물린다.

### Tana — 우리가 만들려는 것의 상용판

> Tana 는 **회의와 업무를 타입 있는 연결 항목으로 자동 변환**하고,
> **권한이 걸린 팀 맥락으로 공유**하고, 새 업무가 들어오면 **계속 갱신**하고,
> Chat 과 **외부 에이전트가 쓸 수 있는 MCP 서버**로 답한다.
>
> 반면 **Notion·Obsidian·Roam 은 연결을 사람이 직접 만들고 유지해야 한다.**

**이게 우리 목표와 거의 같다.** 회의 → 타입 있는 항목 → 팀 공유 → MCP 노출.

> 그래서 *"왜 Tana 를 안 쓰고 직접 만드나"* 에 답할 수 있어야 한다.
> 후보 답: **데이터 소유권 · 락인 회피 · 모노레포 git 과 같은 세계에 두기 ·
> 사내 에이전트(헤르메스)와 직접 연결.** 준범님이 물은 *"철학"* 과 같은 층위의 질문이다.

## 5-10. 마크다운 경로의 표준 4단계 — 우리와 다른 점

[Fountain City 비교](https://fountaincity.tech/resources/blog/agent-memory-knowledge-systems-compared/) 가 "마크다운 + 시맨틱 검색" 경로를 이렇게 정리한다.

```
① 사람이 정본을 유지한다 (Obsidian·git·GitHub wiki)
② 에이전트가 출처를 대며 읽는다
③ 에이전트는 **리뷰 폴더에만 쓴다. 정본에 직접 쓰지 않는다**
④ 사람이 검토해 승격하거나 반려한다
```

**③이 우리와 다르다.** 우리 `handoff` 는 `wiki/` 에 **바로** 쓴다.
사람 검토 단계가 없다.

| 강점 | 약점 |
|---|---|
| 완전한 소유권. 벤더가 사실을 소유하지 않는다 | **시간에 따른 엔티티 추적은 수작업** |
| 사람이 일급 저자 | 긴 세션의 자동 페이징이 까다롭다 |
| 하나의 지식 기반이 여러 에이전트와 팀에 동시에 |  |

**언제 마크다운이 이기나**: 사람이 일급 저자여야 할 때, 이식성·소유권이 중요할 때,
**팀이 이미 마크다운/Obsidian 을 쓸 때** ← 우리가 여기.

**언제 관리형이 이기나**: **시간 기반 질의가 핵심일 때(Zep)**, 장기 에이전트 메모리가
필요할 때(Letta), 인프라 운영 부담을 못 질 때.

## 8. 회의록 용례 — upnorth.ai 가 우리와 같다

```
raw/meetings/              ← 원본 전사본 (immutable)
wiki/people/<name>.md      ← 사람마다. 참석 회의·역할·**미완 약속(open commitments)**
wiki/projects/<project>.md ← 프로젝트마다. 최근 활동
```

**추출 규칙을 `CLAUDE.md` 에 적어둔다:**

> *"결정이란 다음에 해당하는 진술이다 — '우리가 정했다', '합의했다', '이걸로 가자',
> '계획은 …이다'"*

**lint 가 잡는 것:**
- 회의 간 **모순**
- **30일 넘은 미완 약속**
- **한 회의에만 등장한 고아 인물**

우리와의 차이가 분명하다. **우리는 회의 단위로 3종 문서를 만들고 끝**나는데,
이쪽은 **사람·프로젝트·결정 단위로 페이지가 누적**된다.
*"이준범 님이 최근에 뭐라고 하셨지"* 를 물으면 `wiki/people/이준범.md` 한 장이 답한다.

| | |
|---|---|
