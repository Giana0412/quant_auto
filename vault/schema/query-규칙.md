# query 규칙

260811 싱크에서 정한 세 오퍼레이션(ingest / **query** / lint) 중 query 다.

**이게 이 프로젝트의 본질이다.** 설계문서에 이렇게 적어뒀다:

> 기억이 실제로 조회되면 살아 있는 창고고, 아무도(사람도 에이전트도) 안 꺼내 보면 무덤이다.

ingest 와 lint 는 창고를 채우고 정돈하는 일이다. **꺼내 쓰이게 하는 건 query 뿐이다.**

실행: `.claude/skills/ask` 스킬. *"이거 왜 이렇게 했지?"* 같은 말로 부른다.

---

## 1. 절대 규칙 세 가지

```
① 출처 없는 문장은 답변에 넣지 않는다
② vault 에 없으면 "없다" 고 말한다 — 지어내지 않는다
③ personal/ 은 열지 않는다
```

**①이 가장 중요하다.** 근거 없는 답은 그럴듯할수록 위험하다. 사람이 검증할 수
없으면 그건 답이 아니라 추측이다. 모든 문장 뒤에 `[[문서명]]` 이 붙어야 한다.

---

## 2. 찾는 순서

무작정 전체 검색하지 않는다. **위에서부터 순서대로** 본다.

| # | 어디 | 무엇을 얻나 |
|---|---|---|
| 1 | `index/` | 무엇이 있는지부터 파악. 회의 목록·문서 지도 |
| 2 | `wiki/05-meetings/결정사항/` | **결정은 여기가 정본** |
| 3 | `wiki/05-meetings/정리본/` | 그 결정이 나온 맥락과 반대 의견 |
| 4 | `wiki/00-overview/`, `wiki/01-architecture/` | 설계 의도·현재 구조 |
| 5 | `wiki/03-notes/questions.md` | **이미 "모른다"고 기록된 것인지** 확인 |
| 6 | `schema/` | "왜 이런 규칙인가" |
| 7 | `raw/` | 위로 안 풀릴 때만. 원문 확인용 |

**`raw/` 를 마지막에 두는 이유**: 전사본은 길고 오탈자가 많다. 정리본·결정사항이
이미 그걸 해석해 둔 결과물이므로, 해석본을 먼저 보고 원문은 검증할 때만 연다.

---

## 3. 질문의 세 종류

| 종류 | 예 | 주로 어디서 |
|---|---|---|
| **사실** | "회사 캘린더 뭐 쓰지?" | 01-architecture, schema |
| **이유** | "왜 노션 안 쓰기로 했지?" | 결정사항 → 정리본 (반대 의견까지) |
| **이력** | "이거 언제부터 이랬지?" | git 이력 + 결정사항 날짜 |

**"이유" 질문이 vault 의 존재 이유다.** 사실은 코드를 봐도 알 수 있지만, *왜 그렇게
정했는지*는 여기밖에 없다. 이유를 물었는데 결론만 답하면 절반만 답한 것이다 —
**반대 의견과 폐기된 대안까지** 정리본에서 찾아 함께 전한다.

---

## 4. 답변 형식

```
결론 한 줄
  ↓
근거 (언제, 누가, 어떤 자리에서 정했는지)
  ↓
출처 [[문서명]]
  ↓
불확실한 부분이 있으면 그것도 명시
```

**예시**

> **공용 팀 캘린더를 쓰기로 했습니다.**
>
> 2026-08-11 김규형 결정입니다. 그전에는 담당자가 누구든 모든 일정이 김규형
> 캘린더 한 곳에 쌓이는 문제가 있었습니다 — `process-slack-docs.sh` 52행에
> 캘린더 ID 가 하드코딩돼 있었기 때문입니다.
>
> 반려된 대안이 둘 있습니다: 담당자를 참석자로 넣는 방식(커넥터가 attendee 를
> 지원하는지 불확실), 팀원마다 커넥터 연결(자동화 1대 원칙과 충돌).
>
> 출처: [[전체-구조도]] §1-6, [[oao-wiki-설계문서]] §12-8
>
> **아직 안 된 것**: 실제 캘린더 생성과 ID 반영은 미완료입니다.

마지막 줄에 주목할 것. **"정해졌다"와 "실행됐다"를 구분해서 말한다.**

---

## 5. 못 찾았을 때

지어내지 않는다. 대신 이렇게 한다.

```
1. "vault 에 없습니다" 라고 분명히 말한다
2. 어디를 찾아봤는지 밝힌다 (사람이 검색어를 바꿔볼 수 있게)
3. 관련은 있으나 답은 아닌 문서가 있으면 그것만 제시한다
4. 물어볼 사람을 짚어준다 (문서 frontmatter 의 owner)
```

그리고 **`wiki/03-notes/questions.md` 에 추가할지 제안한다.**

> query 가 답을 못 찾았다는 것은 곧 **기록되지 않은 것을 발견했다**는 뜻이다.
> 그걸 questions.md 에 쌓으면 다음번엔 답이 있다. 실패가 자산이 되는 고리다.

---

## 6. 하지 않을 것

| | 왜 |
|---|---|
| `personal/` 열람 | 회사/개인 분리. 애초에 Read 권한을 `vault/` 로 스코프한다 |
| 문서 수정 | query 는 **읽기 전용**이다. 고칠 게 보이면 말만 하고 사람이 정한다 |
| 오래된 문서를 최신처럼 인용 | `updated` 와 `review_by` 를 확인하고, 오래됐으면 그렇다고 밝힌다 |
| 결정사항과 제안을 섞기 | **[결정됨] / [제안] / [미결]** 표기를 그대로 옮긴다 |

마지막 항목이 특히 중요하다. 설계문서는 확정과 제안이 섞여 있고 그걸 표기로
구분해 뒀다. 답변에서 그 구분이 사라지면 **제안이 결정으로 둔갑한다.**
