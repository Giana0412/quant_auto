# 레퍼런스 정밀 대조 — 원문 근거

> 준범님 지목 (0813): **Karpathy llm-wiki · sturlese/stigmergy · GitLab Handbook · PostHog Handbook**
> *"일단 더 찾아봐 그리고 근거도 뚜렷하게"*

**추측을 빼고 원문 인용만 쓴다.** 조사 중 같은 저자의 `cortex`·`hippocampus` 를 추가로
찾아 함께 넣었다 — `stigmergy` 저자 Marc(전직 CTO)가 만든 같은 계열이다.

---

## 0. 가장 중요한 발견 세 줄

**1. 🔴 우리 lint 는 게이트가 아니다.** stigmergy 는 *"모델이 쓰지만 **무엇이 착지할지는
코드가 정한다**"* 고 못박고, diff 에 **결정적 게이트 8개**를 걸어 통과한 것만 커밋한다.
우리 lint 는 *"보고만 하고 고치지 않는다"* — **막지 않는다.** 이게 가장 큰 구조적 격차다.

**2. 🔴 충돌 문제에 이미 답이 있었다.** stigmergy 의 에이전트는 **버리는 git worktree**
안에서 초안을 쓴다. 작업 사본을 건드리지 않으니 사람과 부딪히지 않는다.

**3. ⚠️ 어제 내가 "읽기 경로 = 웹 발행" 이라고 쓴 건 재고가 필요하다.** stigmergy 는
**"별도 read site"를 설계에서 명시적으로 배제**한다. 읽기를 MCP 도구로 준다. §4 참조.

## 1. Karpathy — llm-wiki (원문: `raw/references/`)

우리 구조의 출발점이다. 이미 [[카파시-원문-대조]] 에서 대조했으므로 **아직 안 지킨 것**만.

| 원문 | 우리 |
|---|---|
| *"A single source might touch **10-15 wiki pages**"* | ❌ 새 문서 3개만 만든다. 기존 페이지를 안 건드린다 |
| *"updating entity pages"* — 엔티티 페이지 갱신 | ❌ 엔티티 페이지가 없다 |
| *"noting where new data **contradicts** old claims"* | ❌ 모순을 표시하지 않는다 |
| *"good answers can be **filed back into the wiki**"* | ❌ `ask` 답변이 대화에서 사라진다 |
| *"index.md ... The LLM updates it on **every ingest**"* | ✅ 자동 |
| *"log.md ... `grep "^## \[" log.md \| tail -5`"* | ✅ 그대로 구현 |
| *"the wiki is a **persistent, compounding artifact**"* | ⚠️ 지금은 쌓기만 한다 (compounding 아님) |

> **핵심 문장**: *"The knowledge is compiled once and then **kept current**, not re-derived
> on every query."* — **kept current 가 안 되고 있다.** 우리는 append-only 다.

## 2. 🔴 sturlese / stigmergy — 우리와 가장 가까운 것

> 저장소 설명: *"A team's knowledge, captured where the work happens, filed by an agent,
> and **answered with citations you can check**."*

**우리가 만들려는 것과 문장 단위로 같다.** 그런데 우리가 안 한 것을 다 하고 있다.

### 2-1. 세 가지 약속

| 원문 | 우리 상태 |
|---|---|
| *"knowledge lives in git as markdown in a repository you control"* | ✅ 같다 |
| 🔴 *"a model writes but **code decides what lands**"* | ❌ **없다.** lint 는 보고만 한다 |
| *"**honest refusals beat confident guesses**"* | ✅ `ask` 규칙 ②와 같다 |

### 2-2. 🔴 게이트 8개 — 우리에게 없는 것

에이전트가 만든 **diff 에** 결정적 검사 8개를 돌리고 **통과한 것만 착지시킨다.**

```
zone · binary-page · body-rewrite · secrets · pii · frontmatter · contract · anchoring
```

`gitleaks` 가 PATH 에 없으면 **librarian 이 아예 기동을 거부한다.**

> 우리 lint 7종은 이름이 비슷하지만 **성격이 정반대다.** 우리는 사후 보고,
> 저쪽은 **사전 차단.** 우리 lint-규칙 문서에도 *"자동 수정하지 않는다"* 고 적혀 있다.
> 문제는 수정 여부가 아니라 **막느냐 안 막느냐**다.

### 2-3. 🔴 충돌 해법 — 버리는 worktree

> *"An agent then drafts pages in a **throwaway git worktree**"*

에이전트가 사람의 작업 사본을 안 건드린다. **[[싱크-운영정책-제안]] 의 B(충돌) 문제에
대한 직접적인 답이다.** 우리는 에이전트가 작업 디렉터리에 바로 쓴다.

### 2-4. 엔티티는 사람을 거쳐 태어난다

> *"Entities are **born through a human**: the agent proposes, a steward approves in Slack,
> and only then does a governed writer mint the page and registry entry."*
> 목적: *"세 개의 동일한 고객이 세 가지 철자로 나타나는 것을 막는다"*

단일 기록기 경로는 `ops/entity-registry.json` 하나. 우리 "엔티티 페이지 미구현" 항목의
설계 답이 여기 있다. **자동 생성이 아니라 사람 승인 후 생성이다.**

### 2-5. 인용 검증 — 이번 실행에서 나온 것만

> *"a deterministic verifier traces **every figure and citation back to what the tools
> returned this run**. Untraced figures get withheld; the answer becomes **a refusal
> stating why**."*

우리 `ask` 는 *"출처 없는 문장은 넣지 않는다"* 를 **규칙으로만** 갖고 있다. 저쪽은
**검증기 코드**가 있다.

### 2-6. 권한 — 없는 것과 못 보는 것을 구분하지 않는다

> *"a forbidden page and a non-existent one **return the same string, deliberately**"*

존재 유출을 없애기 위해서다. 우리는 권한 개념 자체가 없다(`personal/` 을 안 여는 규칙뿐).

### 2-7. 🔴 설계에서 **의도적으로 뺀 것** — 여기가 어제 내 제안과 부딪힌다

> 배제 목록: *"**separate read sites**, multiple knowledge repos, **PR ceremony over
> knowledge**, ingest-time figure verification, and SQL over certified datasets.
> This is a knowledge system, not a data warehouse."*

**별도 읽기 사이트를 안 만든다.** 읽기는 MCP 서버의 **고정 도구 10개**로 준다
(`search_brain` `read_page` `list_entities` `describe_entity` `ask` + 쓰기 5개).

**PR 의례도 배제한다.** — 그런데 GitLab·PostHog 는 정확히 그 PR 을 쓴다(§3·§4). **이견이다.**
해소는 §5 에서.

### 2-8. 문서가 아니라 테스트로 강제한다

> *"A layering that lives only in a README is **decoration**; this one is **a test**."*

`tests/test_architecture.py` 가 모듈 import 를 파싱해서 층이 섞이면 **실패시킨다.**

> 우리 [[폴더-규칙]]·[[lint-규칙]] 이 정확히 *"README 에만 사는 층"* 이다.
> `raw/` 수정 금지는 **문장으로만** 있고, lint L6 이 사후에 알려줄 뿐 막지 않는다.

## 2-9. 곁가지 — 같은 저자의 `cortex` (company memory layer blueprint)

> 핵심 원칙: *"**the LLM writes, code verifies — at every layer**; workers act, a supervisor
> learns; every autonomous decision is **budgeted, traced and reversible**."*

우리 미해결 과제에 직접 답하는 게 둘 있다.

| cortex | 우리 미해결 |
|---|---|
| *"Every page carries a verifiable **`as_of`** date grounded in evidence. Near-duplicate revisions form explicit **`supersedes` chains**. Stale information is **demoted rather than silently served**."* | 🔴 "결정이 바뀐다" 문제. 지금은 낡은 결정과 새 결정이 나란히 쌓인다 |
| *"A deterministic validator **re-reads every claimed cell**; hallucinated numbers cannot enter the store."* | 숫자 검증 개념이 없다 |
| *"**Refusal treated as first-class response**"* | ✅ 규칙으로는 있다 |

### `hippocampus` — 역할 분담이 우리와 같다

> *"**You talk to your notes from the terminal; Obsidian is just the (beautiful) viewer.**"*
> *"Obsidian requires **no plugins**; graph view and backlinks work natively."*
> *"The intelligence lives in **the structure, not the infrastructure**."*
> 구성: *"Zero dependencies. One Python script (stdlib only), one shell hook, markdown and git."*

**Obsidian 을 뷰어로만 쓴다.** 플러그인이 필요 없다고 못박는다 — 우리는 obsidian-git
플러그인에 싱크를 맡기고 있다(§[[싱크-운영정책-제안]]). 그리고 **push 는 수동**이다.

| 비개발 직군은 페이지 하단 **"Open Web IDE"** 로 브라우저에서 편집 → MR | GitLab Docs |
| 비기술자용 **"GitLab 101 – a primer for the non-technical"** 을 따로 운영 | 〃 |

> 우리가 "싱크"로 부르는 문제의 상당 부분은 **로컬 사본을 두기로 한 선택의 결과**다.

## 4. PostHog Handbook — 설치 0 으로 기여하는 경로

**비개발자가 핸드북을 고치는 절차가 문서화돼 있다.** 우리에게 가장 실용적인 레퍼런스다.

```
① 페이지의 "Edit this page" 링크
② GitHub 에서 연필 아이콘 클릭
③ 고치고 미리보기
④ 커밋 메시지 입력
⑤ "Create a new branch..." 선택
⑥ "Propose changes" → PR 생성
⑦ 누군가 승인 → "Squash and merge"
⑧ 10~20분 후 자동 반영
```

> **git 설치도, 클론도 필요 없다.** 전 과정이 브라우저에서 끝난다.
> 원문: *"you can easily propose the change by creating a pull request **without having to
> run the full codebase on your computer** — this is a great way to contribute if you're
> in a **less-technical role**."*

문화 쪽 근거도 명확하다.

| 원문 | 함의 |
|---|---|
| *"Almost everything PostHog does is **open for anyone else to edit**, including the Handbook"* | 편집 권한을 좁히지 않는다 |
| *"**Everything should start with a pull request**"* — 가치 *"Why not now?"* | 기본 경로가 PR |
| 🔴 *"We prefer **issues over Slack messages** because it's **public and can sync with the rest of our code workflow**"* | **슬랙보다 git** 을 택한 이유의 원문 |
| *"announcements happen on the appropriate Slack channels **so people can do their work without getting interrupted**"* | 슬랙은 **공지용**, 기록은 git |

> **마지막 두 줄이 우리 "하루 한 번 공유" 논의의 근거가 된다.**
> PostHog 는 **기록(git)과 알림(슬랙)을 분리**했다. 알림을 줄이는 이유도 명시돼 있다 —
> *"방해받지 않고 일하게"*. [[싱크-운영정책-제안]] §5-2 의 분리안과 같은 구조다.

## 5. 🔴 레퍼런스끼리 부딪히는 지점 — 그리고 해소

**GitLab·PostHog 는 PR 게이트를 쓴다. stigmergy 는 "PR 의례"를 명시적으로 배제한다.**
정반대다. 어느 쪽이 맞나.

**누가 쓰느냐가 다르다.**

| | 쓰는 주체 | 무엇으로 막나 |
|---|---|---|
| GitLab · PostHog | **사람** | **사람 리뷰** (MR/PR 승인) |
| stigmergy · cortex | **에이전트** | **코드 게이트** (결정적 검사 8개 / 검증기) |

> **원칙은 같다 — 검증 없이는 착지하지 않는다.** 사람이 쓰면 사람이 보고,
> 에이전트가 쓰면 코드가 본다. 구현만 다르다.

**우리는 에이전트가 쓰는데 게이트가 없다.** 양쪽 어디에도 속하지 않는다. 이게 §0-1 이다.

### 읽기 경로도 같은 방식으로 갈린다

| | 누가 읽나 | 어떻게 |
|---|---|---|
| GitLab · PostHog | **외부 포함 수천 명** | 정적 사이트 |
| stigmergy | **팀** | MCP 도구 — 묻고 인용받는다. 별도 사이트 없음 |
| Karpathy · hippocampus | **개인** | Obsidian 뷰어 + 터미널 대화 |

> **⚠️ 어제 제안 수정.** [[싱크-운영정책-제안]] §4 에서 *"읽기 경로 = 웹 발행(Quartz)"*
> 을 1순위로 놨는데, 레퍼런스를 보면 **팀 규모(6~7명)에서는 질의(ask)가 먼저**다.
> 웹 발행은 GitLab·PostHog 처럼 **수천 명이 브라우징할 때** 값을 한다.
>
> **다만 511개 깨진 위키링크는 여전히 사실이다.** 우선순위가 내려갈 뿐 사라지지 않는다.
> 그리고 PostHog 의 *"Edit this page"* 는 **웹 발행이 있어야 성립하는 경로**다 —
> 비개발자 기여를 원하면 결국 필요하다.

## 7. 이 조사가 바꾸는 것

| | 어제까지 | 지금 |
|---|---|---|
| 1순위 | 읽기 경로(웹 발행) | 🔴 **착지 게이트** — 검증 없이 들어오는 걸 먼저 막는다 |
