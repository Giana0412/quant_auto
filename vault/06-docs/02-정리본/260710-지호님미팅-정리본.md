# 지호님 미팅 — 정리본

- 일시: 2026-07-10 (금) 11:17, 30분 07초

## 1. 한줄 요약

김규형이 대외(마라톤 대회) DB 수집·심사 자동화 파이프라인의 현재 구조를 시연하고 Slack 승인 UX를 확정받은 뒤, 박지호가 이 DB를 실제 영업에 쓰기 위해 필요한 "날짜 기반 알림"과 "유사 스폰서 브랜드 발굴" 니즈를 제시한 미팅.

## 2. 핵심 논의

### 2-1. 대외 DB 수집 파이프라인 현황 (김규형 시연)

- 이벤트 DB **dev** 환경에 연결된 상태로 동작 중
- 수집 소스 4곳: 마라톤고 / 러닝라이프 / 고러닝 / 로드런(마라톤온라인). 마지막 한 곳은 별도 인코딩이 필요해 따로 분리
- 4개 소스에서 추출 → 중복 제거 → 운영사·전화번호·주최·장소·종목·티켓가·공식 출처 URL·날짜 필드로 정리
- 아직 미정인 필드는 **임의로 채우지 않도록** 지시해 비워둔 상태
- 비어 있는 필드는 이후 웹 검색(뉴스 등 4개 소스 외 출처)으로 보강하는 방식

### 2-2. 심사(verify) 에이전트와 Slack 검토 플로우

- 심사 에이전트가 출처 신뢰도를 판정
  - **verified** → 이벤트 DB draft로 자동 반영
  - **needs review**(공식 출처는 아니지만 뉴스 등) / **unreliable**(블로그·네이버 카페 등) → Slack 채널로 검토 요청 발송
- Slack 메시지에는 "대외 정보 업데이트 검토 요청"과 신뢰 등급이 함께 표시됨
- 검토자는 응답(respond) 시 필드 수정 + 승인/반려 선택 가능하며, 승인 후 submit하면 바로 draft로 반영됨
- ※ 전사상 "b 파이드 / 벨 파이드", "닛 리뷰", "어릴 라이브", "윌스/윈스 펀드" 등으로 나오는데 각각 verified / needs review / unreliable / respond를 가리키는 것으로 추정됨

### 2-3. Slack 승인 UX 결정 — 수정 폼 없이 승인·반려만

- 김규형 질문: Slack에서 respond를 눌러 필드 수정 폼까지 띄우는 방식 vs 승인/반려 버튼만 두고 바로 넘기는 방식 중 무엇을 원하는지
- 박지호: Slack에서 **출처 URL을 클릭해 실제 대회인지 확인한 뒤 그 자리에서 바로 승인**할 수 있는 게 베스트
  - 실제로 시연 중 "광제산 트레일러(전사 표기)"를 눌러 실존 대회임을 확인
  - 운영사·대행사·스폰서 같은 항목은 어차피 별도 자동화로 채워지므로 굳이 Slack에서 수정할 필요 없음
- 결론: **승인/반려 결정만 Slack 안에서 보이면 된다**는 방향으로 정리

### 2-4. 아키텍처/인프라 관련 진행 상황

- 구조 자체는 확정 상태. 이상욱(전사 "상호/사모") 지시로 Google Sheet 대신 **CSV/JSON 같은 가벼운 파일 + Git 기반 자동 업데이트**로 전환하기로 되어 있음
- OAO 맥락(컨텍스트) 연결은 아직 미연결. 준범과 상무 간 의견이 갈려 두 사람이 먼저 논의 후 알려주기로 함 — 다만 이 연결 없이도 현재 파이프라인은 정상 동작
  - 쟁점(김규형 전언): 심바·라피키 등 각 에이전트는 **한 작업당 하나의 연동**만 걸어야 충돌이 없다는 준범의 의견. 라피키는 이미 다른 사람이 사용 중이라, 이번 신규 플로우는 심바가 아닌 또 다른 에이전트를 붙여야 한다는 취지
- 현재 자동화는 김규형 개인 PC에서 개인 OpenAI 키로 웹 검색까지 돌고 있음 → **맥미니로 옮겨 상시 구동**하는 것이 다음 단계
- 프로덕션(스튜디오) 반영 시점: 맥미니 연동이 끝나면 바로 가능. 그전까지는 dev에만 쌓이므로 라이브 스튜디오에서는 조회 불가

### 2-5. 박지호의 영업 프로세스와 자동화 니즈

박지호는 이 DB가 "영업의 시작점"이라고 규정하고, 본인 영업 프로세스를 공유한 뒤 두 가지를 요청.

**(1) 날짜 기반 단계별 알림**
- 상품 타임라인: 행사일 기준 6개월~3개월 전에 대회 정보를 인지 → 검색 엔진 도입 제안 → 유가 광고 캠페인 제안
- 영업 단계: 콜드 아웃리치 → 고객 니즈 파악 → 솔루션 비교·검토(제안) → 협상 → 계약(Yes/No)
- 각 단계마다 마감 기한을 정해두고(예: 시작은 대회 3개월 전, 협상은 2개월 전), DB의 기준 날짜와 대조해 **Slack 등으로 자동 알림**을 받고 싶다는 것
  - 예: 3개월 전인데 주최사/대행사 정보가 비어 있으면 알림
  - 예: "지금 아웃바운드 콜드 메일을 보내야 할 시기입니다" 알림
- 김규형이 세일즈맵 API로 Gmail 연동이 가능하다고 언급했으나, 박지호는 **메일 내용을 파싱해 판단하는 게 아니라 본인이 정한 프로세스 기준으로 판단**하는 것이라고 정정
- 메일 라벨링·딜 단계 트래킹까지 붙이는 건 이상적이지만, 박지호 본인이 세일즈맵을 실제로 쓰고 있지 않아 현 단계에서는 사람이 하는 영역으로 남겨둠 (단, "한계를 두지는 말라"고 덧붙임)

**(2) 유사 스폰서 브랜드 리스트업**
- DB에 쌓인 스폰서 리스트를 카테고리별로 정리하고, 유사한 타 브랜드까지 확장 리스트업
- 예: 특정 대회에 보험사가 스폰서로 들어왔다면 유사 보험사 목록을 뽑아 제안 대상으로 활용
- 근거: 실제 스폰서 브랜드만이 잠재 고객이 아니며, 예전엔 사람이 일일이 하던 서치 작업을 AI가 대신할 수 있는 영역이라는 판단
- 김규형은 두 건 모두 구현 가능하다고 답변

### 2-6. 프로젝트화 제안

- 박지호: 니즈와 구현 목표에 **목표 날짜를 하나 찍고 프로젝트화**해서 실제로 굴러가는지 보자는 제안
- 원하는 시점은 **7월 말**. 다만 "이건 더 쉬울 것 같고, 오히려 에이전트화 관점에서 더 할 수 있는 게 뭔지 김규형 의견을 듣고 싶다"는 취지

## 3. 맥락 / 배경

- 이 미팅 전에 김규형이 이상욱과 구조를 논의해 "구조는 바꾸지 말 것, Google Sheet 대신 가벼운 파일 + Git으로" 방향을 이미 받아둔 상태였고, 이번 자리는 **실사용자인 박지호의 UX 니즈를 확인**하는 성격
- 박지호는 "지난번에도 한 번 설명했다"며 영업 프로세스를 재차 설명 — DB 구축 자체보다 그 뒤 영업 활용 단계로 논의 축이 이동한 시점
- 이메일/세일즈맵 관련해서는 이전에 백필 작업을 하며 권한을 받아둔 이력이 있음

## 4. 미결정 사항 / 추가 논의 필요

- OAO 맥락 연결 방식 — 준범과 상무 간 의견 차이가 있어 두 사람이 별도 세션을 잡고 결정 예정. 어느 에이전트(심바/라피키/제3의 에이전트)에 붙일지 미정
- 영업 단계별 기한 수치(3개월/2개월 등) — 박지호가 이상욱과 논의해 확정 예정
- 세일즈맵 연동 여부 — 박지호가 실제로 쓰고 있지 않아 현 단계에서는 보류, Slack 알림 우선
- 메일 단계 트래킹(라벨링 기반 딜 스테이지 관리)은 "아직 바라지 않는" 영역으로 남김
- 비어 있는 필드를 주기적으로 재체크하는 루프는 돌아가지만, 수동 트리거가 필요할 수 있어 김규형이 일단 보류해둔 상태
- 프로덕션 이관 시점 — 맥미니 연동 완료 시점에 종속
