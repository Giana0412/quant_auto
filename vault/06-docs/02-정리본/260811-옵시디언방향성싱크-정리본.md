# 옵시디언 방향성 싱크 — 정리본

- 일시: 2026-08-11
- 참석자: 김규형, 이준범

---

## 한 줄 요약
이번 회의의 결론은 **옵시디언 도입의 핵심을 도구 연결보다 OAO 위키 구조와 운영 원칙(ingest / query / lint) 설계에 두자**는 것입니다.

## 배경
김규형님은 각자 로컬 볼트, git 동기화, 맥미니 자동화, Slack/Google Calendar/Claude 연동까지 포함한 방향을 설명했습니다. 이준범님은 이 구조가 도구 연결에 비해 위키 구조와 에이전트 운영 원칙 정의가 상대적으로 약하다고 보고, Andrej Karpathy식 LLM Wiki 관점에서 재정리를 제안했습니다.

## 핵심 논의

### 1. 중심축은 맥미니가 아니라 OAO 위키
- 맥미니가 업데이트를 받아 반영하는 구조보다, git 기반의 OAO 위키 자체가 회사의 최상위 지식 저장소가 되어야 함
- 사람과 에이전트 모두 이 위키를 읽고 일을 하도록 설계해야 함
- 맥미니는 위키를 활용하는 실행 주체 중 하나일 뿐 중심축이 아님

### 2. Claude 계정 종속 설계는 피해야 함
- 커넥터를 Claude 계정에 붙이는 방향은 특정 LLM에 종속될 위험이 있음
- 향후 GPT, Gemini 등 다른 모델로 옮겨도 같은 작업이 가능해야 함
- 공용으로 공유할 것은 위키 구조/스킬/설정 규약이고, 개인 토큰과 개인 계정값은 각자 로컬 환경에 분리되어야 함

### 3. 플러그인 사용 여부는 본질이 아님
- Obsidian Git 플러그인, 런치패드, 자체 커맨드 중 무엇을 쓰는지는 방법론 문제임
- 중요한 것은 위에 얹는 구조와 운영 원칙임
- 즉 플러그인 사용 여부보다
  1) 위키 구조
  2) sync 방식
  3) ingest/query/lint 운영 원칙
  이 먼저 정의되어야 함

### 4. 현재 초안은 LLM Wiki 핵심 요소가 아직 약함
이준범님이 부족하다고 본 지점:
- raw / wiki / schema 분리
- index / log 설계
- ingest / query / lint 정의
- 에이전트가 위키를 어떻게 읽고 정리하는지에 대한 역할 정의

즉 "옵시디언을 어떻게 연결할까"는 많이 보였지만, "LLM이 쓰기 좋은 위키를 어떻게 운영할까"는 덜 정리된 상태로 평가됨

### 5. 도서관 비유로 구조를 재정의
이준범님은 OAO 위키를 도서관에 비유함.
- **위키**: 회사의 정리된 책과 공용 지식
- **raw**: 회의 전사본, 슬랙 로그, 외부 문서 같은 원본 자료
- **schema**: 도서관의 분류 체계와 운영 규칙
- **Hermes/에이전트**: raw를 정리하고 낡은 책을 정리하며 연결성을 강화하는 사서

이 구조를 전제로 해야 사람과 에이전트가 같은 지식 체계를 활용할 수 있다는 관점이 공유됨

### 6. 회의록 인입은 더 단순해야 함
- 슬랙 앱 → 옵시디언 플러그인 → Claude → 액션아이템 추출 구조는 테스트용으로는 가능하지만 기본 아키텍처가 되어야 하지는 않음
- 더 기본적인 흐름은
  1) 누군가 회의 전사본을 raw에 넣고
  2) 에이전트가 ingest하여 wiki로 정리하고
  3) 필요하면 결정사항/액션아이템/정리본을 추가 생성하는 형태
- 슬랙은 필요 시 쓰는 인터페이스이지 데이터 인입의 중심축은 아님

### 7. Hermes 역할은 '사서'
- raw 파일이 들어오면 적절한 위키 위치로 정리
- 오래된 문서 정리 및 통합
- 링크 강화
- 주기적인 lint 수행으로 중복 제거, 위치 재배치, 구조 정비
- 지속적으로 살아 있는 위키를 유지하는 관리 주체

## 결론
이번 싱크는 "옵시디언 연결 방법"보다 **OAO 위키를 사람과 에이전트가 함께 쓰는 도서관으로 어떻게 설계할지**를 다시 맞춘 회의였습니다. 실제 Slack/Calendar/플러그인 연동 같은 유즈케이스는 그 위에 얹는 2차 작업으로 보고, 우선 위키 구조와 운영 원칙을 재설계하기로 방향이 모였습니다.
