# 이벤트 리서치 & 옵시디언 방향성 논의 — 정리본

- 일시: 2026-08-03 (월) 15:06, 52분 5초

## 1. 한줄 요약

이벤트 리서치 enrich 스킬의 검수 방법(테스트 케이스 문서화 + 이준범이 랜덤 이벤트로 직접 검증)을 정하고, 옵시디언 도입 방향을 "각 팀이 노션/깃으로 나눠 쓰는 안"에서 "모두가 옵시디언 깃 레포에 다이렉트로 쓰고, 비개발자는 스킬 한 마디로 PR·머지까지 자동화하는 안"으로 뒤집은 회의.

## 2. 핵심 논의

### 2-1. enrich 스킬 검증 순서 — 이준범이 제안한 테스트 방식

이준범이 제시한 순서는 다음과 같다.

1. **기존(이미 있던) 이벤트부터 enrich로 정보를 채운다.** discover로 새로 찾으라는 게 아니라, 이미 등록된 이벤트에 대해 enrich를 돌려 소스를 다 채우는 것. 이유는 "모든 이벤트에 소스가 있어야 비교가 유의미하다"는 것.
2. 그다음 **discover가 이미 찾아놨지만 draft 상태로 남아 있는 이벤트들**을 하나하나 enrich로 채운다.
3. 문제없이 채워진 목록을 김규형이 알려주면, **이준범이 draft → publish로 전환**한다.

### 2-2. 슬랙 반영 테스트를 어떻게 할 것인가

- 현재 슬랙에 알림이 오지 않고 있어서 "실제 반영 + 슬랙 알림" 경로가 테스트되지 않은 상태 — 이준범이 이 부분을 먼저 짚음.
- 이준범 제안: **draft 이벤트는 아직 배포된 게 아니니, 정보가 채워지면 바로 반영해도 되고 슬랙 알림이 와도 된다.** 즉 draft 이벤트에 enrich를 그냥 돌려서 슬랙 반영/알림 경로를 실제로 태워보는 방식.
  - 회의 중 예시로 "사우나론인 특선 한강 공원"(전사 오기 추정)류의 draft 이벤트를 바로 돌려보자고 했으나, 이때 애플 결제 이슈가 터져 실제 시연은 이뤄지지 않음.

### 2-3. 이준범의 최종 검수 방식 — 랜덤 10개

- "작업 끝났다"는 보고를 받으면 **이준범이 직접 특정 이벤트 ID를 던져 enrich를 돌리게 하고**, 슬랙으로 오는 알림(없던 정보 중 무엇을 채웠고, 있던 정보 중 무엇을 바꿨는지)을 확인한다.
- 그 알림을 들고 **실제 사이트에 직접 들어가 눈으로 본 정보와 대조**한다. "내가 얻을 수 있는 정보를 얘가 다 가져왔다"면 그게 100%.
- 표본은 **랜덤 10개 사이트**. "10개 다 들고 왔으면 100개도 되고 1000개도 된다고 판단할 것 같다"는 논리.
- 일정: **8월 4일(화) 오전, 점심 전에** 이준범이 랜덤 이벤트를 뽑아주면 김규형이 돌리고, 점심 후 결과를 함께 확인하기로 함.

### 2-4. 테스트 케이스(TC) 문서화

- 지금 김규형이 만들어 둔 것은 **TC가 아니라 "검증해야 할 항목을 분류해 놓은 목록"**이라는 게 이준범의 지적.
- 제대로 된 TC는 T0 / T0-1 / T0-2 / T1 … 식으로 번호가 붙고, **각 케이스의 통과 여부를 하나하나 판정할 수 있어야** 한다.
  - 예: "공식 페이지 가져오기"가 T0이라면 → T0-1 정적 index.html 페이지, T0-2 SPA(리액트 등), T0-3 Next.js, 그다음 PHP로 구현된 사이트… 사이트 구현 방식별로 케이스를 쪼갠다.
- 작성 방법: **지금 있는 목록을 그대로 클로드에 넣고 TC를 만들어달라고 한 뒤, 결과를 이준범에게 보여주면 이준범이 검토**한다.
- 배경: 이상욱이 "테스트 케이스를 작성해 본 적이 있느냐, TC를 본 적이 있느냐"고 물었던 것과 연결된 논의. 문서화가 되어야 이상욱이 기대하는 형태의 테스트 케이스가 된다.

### 2-5. 비용과 운영 규모

- 비전을 안 쓰는 경우 케이스당 약 **$0.2**, 비전이 들어가면 **$1~1.5**. 이미지 분할까지 하면 2배지만 **$5 이내면 커버**된다고 보고 그대로 진행하기로 함.
- 이준범: 이건 현금 지출이 아니라 **Max(프로 20배) 플랜 토큰 한도 내에서 쓰는 것**. 5시간 세션에 $100 이상은 충분히 커버된다는 판단.
- 규모 계산: 전체 대회 약 **700개**, 그중 미래 대회 **300개 남짓**. 쿨타임 7일 기준으로 7로 나누면 **하루 약 50개**. 새벽에 50개씩, 전부 비전을 써서 개당 $2로 잡아도 $100 수준 → 출근 시점에 세션이 만료될 정도는 아니라고 보고 **새벽 배치 운영 OK**.
  - 만약 세션이 만료되면 다음 날로 미루거나, 여유 있을 때 수동으로 돌려도 된다는 입장.

### 2-6. 완성도 — 80% → 90%로 재정의

- 김규형 자평: **80%**. 우려 지점은 소규모 대회 — 공식 SNS 없이 블로그/카페만 있는 경우 스폰서 등의 정보가 잘 안 잡힘.
- 이준범: 그건 추가 작업 영역. **"공식 사이트만 잘 긁어오는 것"까지를 일단 100%로 정의**하고, 기사·블로그·인스타 확장은 그 이후에 하는 게 낫다.
- 이 기준으로 재조정하니 **약 90%**. 나머지 10%는 슬랙 알림 포함 테스트를 몇 번 돌려본 뒤 마무리하기로.

### 2-7. 클리포드(전사상 "클2/클투") 다중 대회 사이트 이슈

- 문제: discover가 개별 대회 페이지가 아니라 **운영사 메인 화면을 소스 URL로 넣음**. 마라톤고 같은 애그리게이터가 운영사 메인 사이트를 소스로 걸고 있기 때문. 실제로는 한 운영사 아래에 "굿모닝 스타필드", 시즌 런투어 등 여러 대회가 붙어 있음.
- 이준범 지시: **discover 단계에서 소스 URL을 개별 대회(프로덕트) 페이지까지 지정해 넣어두고, 그 상태에서 enrich가 잘 도는지 확인**할 것.
- 추가로 발견된 렌더링 이슈: 해당 상세 페이지가 **통째로 아주 긴 이미지** → 비전이 텍스트를 착각하거나 아래쪽 항목을 누락. **이미지를 분할해서 보게 하니 정확도가 크게 올라갔고, 대신 비용이 2배**.
- 결론: **기능상 문제는 없고 비용만 오르는 것**이므로 이미지 분할 방식으로 진행.

### 2-8. 옵시디언을 왜 쓰는가 — "메모리 vs CPU"

- 김규형의 초기 구상: 노션/드라이브/슬랙/깃에 흩어진 회사 맥락을 옵시디언에 모으고, 각 팀은 익숙한 툴(세일즈=노션, 개발=깃)을 맥락 입력 통로로 쓴다.
- 김규형이 예로 든 세일즈 플로우: 이벤트 DB에서 D-90, D-80 식으로 스폰서 연락 타이밍을 자동 계산 → 슬랙 알림 → 담당자가 딜 진행 후 상태 업데이트 → 플러그인 통해 옵시디언에 자동 반영 → 이상욱이 "이거 하셨어요?"라고 묻지 않아도 상태를 알 수 있게.
- 이준범의 반론: **그 역할을 하는 건 옵시디언이 아니라 헤르메스 에이전트**다. 옵시디언은 그 일을 하지 않고, 결국 스킬들이 한다.
- 여기서 나온 정리가 이 회의의 핵심 프레임: **옵시디언 = 메모리, 헤르메스 에이전트 = CPU(연산).** 뇌 안에서 기억을 담당하는 부분이 옵시디언, 연산을 담당하는 부분이 헤르메스. 지금 메모리가 여러 군데 분산돼 있으니 최대한 옵시디언 한 곳에 모아서 헤르메스가 연산하기 쉽게 만드는 것이 목적.
- 또 하나: 옵시디언이 각광받는 이유는 노트 앱이라서가 아니라 **클로드와 함께 썼을 때의 효과** 때문. 노션은 문서를 클로드에게 시키고 복붙해서 올려야 하지만, 옵시디언은 오르카에 클로드 창 하나 띄워놓으면 MD 파일을 알아서 넣고 찾아준다.

### 2-9. 각 툴의 역할 정리

- **노션**: 옵시디언을 도입하면 **아예 안 쓸 것 같다**(이준범). 세일즈도 노션이 아니라 바로 옵시디언을 쓰게 하는 방향.
- **깃**: 옵시디언 데이터 갱신을 위해 살아 있어야 함.
- **구글 드라이브**: 용량이 큰 원본 파일 보관용. 옵시디언에는 MD 파일만 들어가야 하므로 원본은 드라이브와 오간다.
- **슬랙**: 이준범은 처음에 "내용을 꺼내는 용도로만" 쓸 것 같다고 했으나, 김규형이 회의록·오늘의 할 일을 이미 슬랙에 올리고 있으니 연동해서 자동 입력하자고 하자 **"그게 맞겠다"고 동의**(입력 통로로 슬랙이 편하다는 이유).

### 2-10. 동기화 방식 3안 비교

| 방식 | 장점 | 단점 |
|---|---|---|
| 옵시디언 Sync (공식·유료, 인당 약 $5) | 실시간 동기화, 별도 개념 학습 불필요 | 동시 편집 시 크래시 → 내용이 섞이거나 유실 가능. 유료 |
| Git | 충돌 시 방어막(PR·리뷰)이 있음 | 실시간 동기화 안 됨. 커밋/푸시/PR 개념 필요 → 비개발자에게 부담 |
| 클라우드 드라이브(iCloud/구글) | 실시간 공유 | 플랫폼(맥/윈도우)에 따라 동작이 다르고 모바일에서 안 되는 등 제약 |

- 노션 연동 플러그인도 검토했으나, **노션에 적힌 마크다운 내용만 넘어오고 버튼 같은 기능은 옵시디언으로 넘어오지 않는다**는 한계가 있음.
- 유료 결제에 대해: 쓸 가치가 있으면 쓰겠지만 **연간 결제는 안 할 것 같다** — "1년 안에 옵시디언 유행이 지날 수도 있다"는 이유.
- 김규형: 맥락 입력 방법 자체를 전사적으로 통일할 필요는 없고, 각 팀에서 그 단점이 별로 중요하지 않을 수도 있다는 의견도 냄. 다만 "그렇게 따지면 옵시디언에 다이렉트로 넣는 게 가장 덜 귀찮다"고 스스로 인정.

### 2-11. 슬랙 → 옵시디언 플러그인의 동작 방식 (이준범 확인 질문)

- 이준범이 "옵시디언은 로컬 저장소인데 플러그인이 어떻게 떠 있느냐"고 계속 물었고, 김규형이 정리한 답:
  - 별도 서버를 띄우는 게 아니라, **옵시디언 플러그인이 슬랙 API를 호출해 메시지를 가져오고, 그것을 MD 파일로 변환**한다.
  - 저장 위치는 **맥미니 로컬**(메인 vault).
  - 변환 과정에서 옵시디언 템플릿에 맞춰 정리되며, 연결된 제미나이/클로드가 **자동 요약**까지 해준다.
- 이 흐름대로면 ClovaNote TXT를 슬랙에 올리기만 하면 플러그인이 감지해 옵시디언에 회의록이 생성되고, 심바가 드라이브로 전사본을 내보내던 과정을 대체할 수 있다는 게 김규형의 그림.
- 다만 어느 방식이든 **맥미니 로컬에 저장된 것을 깃이든 Sync든으로 팀에 전파하는 문제는 남는다**는 것이 이준범의 정리.

### 2-12. 방향 전환 — "다 썼다, 넘겨줘" 스킬

회의 끝부분에서 방향이 뒤집혔다.

- 이준범이 이상적 모델로 언급한 것은 **안드레 카파시(Andrej Karpathy)의 위키 방식** — 모든 유저가 같은 위키를 기반으로 클로드로 문서를 작성·호출하고, 생성된 데이터가 실시간 동기화되는 형태.
- 구조: **모노레포와 별도로 옵시디언 전용 위키 레포를 하나 둔다.** 비개발자는 모노레포를 볼 필요 없이 옵시디언 레포만 바라보고, 오르카에서 바로 문서 생성 → PR까지. 원본은 맥미니에서 관리.
- 김규형의 제안이 결정적이었음: 오르카가 스스로 머지도 하고 PR도 돌리니, **비개발자도 "다 썼으니 넘겨줘"라고만 하면 되지 않느냐**.
- 이준범 동의: **자동으로 PR을 올리고 머지까지 하고 풀 받아 "최신화됐다"까지 해주는 스킬을 만들어 두면**, 일반 유저는 커밋·PR·푸시 개념 없이 "이거 업데이트해줘"만 하면 된다. **그러면 깃으로 가도 괜찮다.**
- 이 결론에 따라 슬랙 플러그인 경유 방식의 필요성도 줄어듦 — 슬랙에 올리고 시키는 대신 **오르카에서 텍스트를 그대로 올리고 "이거 넘겨달라"고 하면 템플릿 변환해서 회의록이 저장되는 쪽이 훨씬 빠르다**는 데 두 사람 모두 동의.
- 역할 분담 그림: **오르카가 팔다리로 정보를 수집·생성**하고, **헤르메스 에이전트(뇌)는 결정사항 등 정말 필요한 때에만** 쓰이게 한다.
- 파일 구조에 대해서는 이준범이 "카파시 것 그대로 쓴 것 같다"며 **좋다고 평가**.

## 3. 맥락 / 배경

- 이 회의는 (1) 이벤트 리서치 enrich 스킬의 완성도 점검·검수 방법 합의, (2) 옵시디언 도입 방향성 논의 두 갈래로 진행됐다.
- TC 문서화 요구는 이상욱이 앞선 자리에서 "테스트 케이스를 작성해 본 적 있느냐"고 물은 데서 이어진 것.
- 옵시디언 논의는 김규형이 세일즈/개발을 나눠 각각 노션·깃을 쓰는 안을 준비해 왔으나, 이준범이 "옵시디언은 메모리, 헤르메스는 CPU"라는 프레임으로 되짚으면서 전원이 옵시디언에 다이렉트로 쓰는 안으로 정리됐다.
- 회의 중반(약 14분~19분, 39분~43분) 애플 인앱결제 검증 오류 이슈가 터져 옆자리 대응 대화가 끼어들었고, 이 때문에 draft 이벤트 enrich 실시간 시연은 이뤄지지 않았다. (해당 이슈는 이 회의의 안건이 아님)

## 4. 미결정 사항 / 추가 논의 필요

- **동기화 방식 최종 확정**: 깃 + 자동화 스킬 방향으로 기울었으나 "이 방향으로 다시 디벨롭해 보자" 단계이며, Sync 유료 결제 여부도 "월 단위면 몰라도 연간은 안 한다" 정도로만 정리됨.
- **enrich 이후 작업 범위**: 기사·블로그·인스타 등 비공식 소스 확장은 공식 사이트 100% 이후로 미룸.
- **enrich 스킬 이후의 후속 작업 계획**: 8월 4일에 다시 논의하기로 함.
- **슬랙 → 옵시디언 플러그인 채택 여부**: 오르카 직접 방식으로 기울면서 사실상 후순위가 됐으나 명시적으로 폐기하지는 않음.
