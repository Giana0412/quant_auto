## 0. 한 장 요약

```
   ┌─ 사람 쪽 (각자 노트북) ────────────┐   ┌─ 자동화 쪽 (맥미니, 이전 예정) ──┐
   │                                  │   │                                │
   │   Obsidian ......... 읽기·검색    │   │   launchd ........... 시계      │
   │   Orca + Claude .... 쓰기·정리    │   │     └ Claude CLI .... 일꾼      │
   │                                  │   │                                │
   │   vault 사본 (통째로 전부)         │   │   vault 사본 (통째로 전부)       │
   └────────────────┬─────────────────┘   └───────────────┬────────────────┘
                    │                                     │
              "넘겨줘 / 받아줘"                        (자동 반영)
                    │                                     │
                    └──────────────┐       ┌──────────────┘
                                   ▼       ▼
                        ╔═══════════════════════════╗
                        ║   GitHub — 유일한 공유점    ║
                        ║   여기 없으면 공유 안 된 것   ║
                        ╚═══════════════════════════╝

**핵심 3가지**

1. **우리가 운영하는 서버는 0대다.** GitHub이 서버 역할을 대신한다.
2. **모든 기기가 vault 전체 사본을 갖는다.** 일부만 받아오는 구조가 아니다.
3. **GitHub에 올라가야 공유된 것이다.** 내 노트북에만 있으면 나만 아는 상태다.

## 1. 서버 — 무엇을 쓰는가

### 1-1. 우리가 운영하는 서버: 없음

띄워놓고 관리하는 서버, DB, 백엔드가 **하나도 없다.** 계정 관리 화면도, 접속 URL도, 서버 요금도 없다. 대신 **남이 운영하는 서비스 5곳**에 얹혀 있다.

### 1-2. 빌려 쓰는 외부 서비스 4곳

| # | 서비스 | 누구 서버인가 | 무엇에 쓰는가 | 끊기면 |
|---|---|---|---|---|
| 1 | **GitHub** | Microsoft | vault 공유·이력 보관. **유일한 필수** | 공유가 멈춤. 각자 노트북 사본은 멀쩡 |
| 2 | **Anthropic** (Claude) | Anthropic | 쓰기·정리를 실제로 수행 | 자동 정리가 멈춤. 손으로 쓰면 됨 |
| 3 | **Slack API** | Salesforce | 회의 원본 수집, 기한 문의 게시, 실패 알림 | 수집이 멈춤. 붙여넣기로 대체 가능 |
| 4 | **Google Calendar** | Google | 액션 아이템 기한 등록 | 캘린더 등록만 멈춤 |

```
                        각 기기 (노트북 · 맥미니)
                                 │
        ┌───────────┬────────────┼────────────┐
        ▼           ▼            ▼            ▼
   ┌─────────┐ ┌─────────┐  ┌─────────┐  ┌─────────┐
   │ GitHub  │ │Anthropic│  │  Slack  │  │ Google  │
   │         │ │         │  │   API   │  │Calendar │
   ├─────────┤ ├─────────┤  ├─────────┤  ├─────────┤
   │ 필수 🔴  │ │자동화 필수│  │수집·알림 │  │ 일정용   │
   └─────────┘ └─────────┘  └─────────┘  └─────────┘
    HTTPS       Claude CLI   slack.com    claude.ai
    git push                 /api/*        커넥터
```

> 회사 자동화가 쓰는 채널은 **Slack 하나로 통일한다.** 수집·기한 문의·실패 알림이
> 전부 같은 채널에서 일어나므로 별도 알림 서비스를 추가하지 않는다.

### 1-3. 인증 정보가 어디에 있는가

| 무엇 | 어디에 | 상태 |
|---|---|---|
| GitHub 인증 | 각자 노트북의 git 자격증명 | 개인별 |
| Claude 계정 | 각자 로그인 (**좌석 필요 — 설계문서 §12-5 미결 🔴**) | 미해결 |
| Slack 토큰 | 현재 **slack-sync 플러그인의 `data.json` 안** | ⚠️ 플러그인 제거 전 이관 필요 |
| 회사 캘린더 | claude.ai 계정의 커넥터 설정 (로컬 파일에 없음) | 계정 종속 |

> ⚠️ **Slack 토큰은 플러그인 안에만 있다.** 플러그인을 지우면 토큰이 같이 사라지고, `process-slack-docs.sh` 63행이 그 파일을 읽고 있어서 2단계가 조용히 깨진다. → 개편안 **B-0**이 이걸 먼저 처리한다.

### 1-4. 회사 캘린더 vs 개인 캘린더 (절대 섞이면 안 됨)

```
회사 결정사항  ──▶  mcp__claude_ai_Google_Calendar__*  ──▶  gkimam@oao-corp.com
                    (claude.ai 커넥터)                        ← 캘린더ID 명시 고정

개인 일정      ──▶  mcp__google-calendar-personal__*   ──▶  kimgyuh04@gmail.com
                    (로컬 MCP 서버)                          ← 회사 경로에서 호출 금지
```

`process-slack-docs.sh`는 `--allowedTools`에 회사 도구만 넣어서 물리적으로 개인 캘린더에 접근할 수 없게 막아뒀다.

### 1-5. 커넥터는 플러그인이 아니라 **계정**에 붙는다

Gmail·Drive·Calendar 연동은 Obsidian 플러그인이 아니라 **claude.ai 계정에 붙는 커넥터**다.
`.obsidian/`에도, git에도 들어있지 않다. 그래서 **vault를 clone해도 따라오지 않는다.**

→ 그러면 팀원은 못 쓰는 것 아닌가? **맞다. 그리고 그래도 된다.**

| 커넥터 | 지금 누가 쓰나 | 무엇에 | 팀원에게 필요한가 |
|---|---|---|---|
| **Gmail** | `archive-newsletters.sh` | `personal/09-newsletters` (**로컬 전용 repo**, 회사 vault 아님) | **아니오** — 개인 영역 |
| **Google Drive** | **어떤 스크립트도 안 씀** (실측) | — | **아니오** |
| **Google Calendar** | `process-slack-docs.sh` STAGE2 | 액션 아이템 기한 등록 | **아니오** — 자동화 머신 1대만 |

> **Drive에 대한 오해 주의.** 설계문서 곳곳의 "큰 파일은 Drive에 두고 링크만 건다"는
> **사람이 지키는 규칙**이지 자동 연동이 아니다. 팀원은 평소처럼 Drive를 쓰면 되고,
> vault에는 링크를 붙여넣을 뿐이다. 커넥터가 필요 없다.

**팀원의 작업 경로에는 커넥터가 0개 필요하다.**

```
  읽기 :  Obsidian ────────────▶ 로컬 파일          커넥터 불필요
  쓰기 :  Orca + Claude ───────▶ 로컬 파일 + git   커넥터 불필요
  공유 :  "넘겨줘 / 받아줘" ────▶ GitHub            커넥터 불필요

  커넥터가 필요한 곳은 여기 한 곳뿐:
          자동화 머신 1대 (김규형 계정) ──▶ Calendar
```

### 1-6. ⚠️ 진짜 문제는 반대쪽에 있다 — 일정이 한 사람에게만 쌓인다

커넥터가 계정에 묶여 있어서 생기는 실제 결함은 "팀원이 못 쓴다"가 아니라 이것이다.

`process-slack-docs.sh` 52행이 캘린더를 **한 개로 고정**하고 있다.

```bash
STAGE2_CALENDAR_ID="gkimam@oao-corp.com"   # 하드코딩
```

```
  결정사항의 액션 아이템:  "[이준범] 이벤트 DB 스키마 확정"
                              │
                              ▼
        제목만 "[이준범] …" 이고, 일정은 김규형 캘린더에 생성됨
                              │
                              ▼
        이준범 캘린더에는 아무것도 안 뜬다  ✗
```

담당자가 누구든 **모든 일정이 김규형 캘린더 한 곳에 쌓인다.** 담당자 본인은 Slack 당일
알림(`<@담당자>님, 오늘 이거 해야 함`)만 받고, 자기 캘린더에서는 볼 수 없다.

**해결 후보 3가지**

**[결정됨] 공용 팀 캘린더를 하나 만들고 전원이 구독한다.** (2026-08-11, 김규형)

```
        결정사항 액션 아이템
               │
               ▼
     ┌──────────────────────┐
     │  OAO 공용 팀 캘린더    │  ← STAGE2가 여기에만 쓴다
     └──────────────────────┘
               │
     ┌─────────┼─────────┬─────────┐
     ▼         ▼         ▼         ▼
   김규형    이준범    박지호    이상욱     ← 각자 구독. 자기 캘린더에 뜬다
```

- 커넥터 추가 **0개**. 자동화는 계속 1대에서만 돈다.
- 반려된 대안: 담당자를 참석자(attendee)로 넣기 → 커넥터의 `create_event`가
  attendee를 지원하는지 불확실. 팀원마다 커넥터 연결 → 자동화 1대 원칙(결정 #11)이 깨진다.

**남은 작업 (사람이 해야 함 — 브라우저 작업)**

| | 할 일 |
|---|---|
| 1 | Google Workspace에서 공용 캘린더 생성 (예: `OAO 액션아이템`) |
| 2 | 팀원 전원에게 공유 + 자동화 계정에 **쓰기 권한** 부여 |
| 3 | 캘린더 ID 확보 (`…@group.calendar.google.com` 형태) |
| 4 | → 그 ID를 알려주시면 `process-slack-docs.sh` 52행 한 줄만 바꾸면 끝난다 |

이것으로 설계문서 §12-5(팀원 좌석)가 풀린다. 대신 **딱 하나의 규칙**이 새로 생기고,
그 규칙이 아래 이메일 문제의 답을 결정한다.

```
  ╔══════════════════════════════════════════════════════╗
  ║  공용 계정에 붙인 커넥터는                              ║
  ║  그 계정을 쓰는 사람 전원이 접근할 수 있다.               ║
  ╚══════════════════════════════════════════════════════╝

     캘린더를 "공용 캘린더"로 판 이유가 이것이다.
     개인 캘린더를 붙였다면 전원이 그 사람 일정을 다 보게 된다.
```

**같이 짚어둘 것 3가지** (결정을 되돌리자는 게 아니라, 알고 쓰자는 것)

| | 내용 |
|---|---|
| 사용량 | 한도를 전원이 나눠 쓴다. 동시에 몰리면 서로 느려질 수 있다 |
| 추적 | 누가 무엇을 시켰는지 계정 기록으로 구분되지 않는다 |
| 약관 | 요금제가 좌석 단위인 경우 공용 사용이 맞는지 **확인 필요** |

## 1-8. 이메일 세일즈 내용을 전원이 보게 하기

### 하고 싶은 것

```
   세일즈 메일  ──▶  세일즈 담당이 슬랙에서 리뷰  ──▶  ???  ──▶  전원이 봄
                     (지금 여기까지는 하고 있음)
```

`???`를 채우는 것이 과제다. 정확히는 **Slack에서 보이게** 하는 게 아니라
(그건 이미 된다) **vault에 남아서 검색되고 나중에 맥락으로 쓰이게** 하는 것이다.
Slack 메시지는 흘러가고, vault는 남는다.

### 방법 3가지

| | 방법 | 커넥터 | 평가 |
|---|---|---|---|
| **A** | **세일즈 Slack 채널을 수집원에 추가** → `vault/08-sales/` | 0개 | ✅ **권함** (착지점은 수정 — 아래) |
| B | 공용 메일함(`sales@…`)을 만들고 거기에만 Gmail 커넥터 | 1개 | 나중에. 사람 개입 없이 자동 수집이 필요해지면 |
| C | 세일즈 담당 **개인 메일함**에 Gmail 커넥터 | 1개 | ❌ **반대 — §1-7 규칙 위반** |

### C를 반대하는 이유

§1-7의 규칙 때문이다. 공용 계정에 개인 메일함을 붙이면
**그 계정을 쓰는 전원이 그 사람 받은편지함 전체를 읽을 수 있게 된다.**
세일즈 메일만 골라 보이는 게 아니다. 급여·인사·개인 메일이 전부 열린다.

### A — 권하는 방법

```
  세일즈 메일 ──▶ 세일즈 담당 ──▶ #sales 채널에 올림
                  (읽고 판단)          │
                                       │  slack-collect.sh (1시간마다)
                                       ▼
                              vault/08-sales/ ──▶ GitHub ──▶ 전원
```

**사람이 한 번 거르는 것이 이 설계의 약점이 아니라 장점이다.**
메일함을 통째로 빨아들이면 개인 메일·무관한 메일·거래처 기밀이 전부 vault로 들어간다.
세일즈 담당이 **"이건 회사 기억에 남겨야 한다"** 고 판단한 것만 올라간다.
그리고 이미 그 리뷰를 하고 있다 — 새로 생기는 일이 없다.

**비용이 사실상 0인 이유**

| | |
|---|---|
| 커넥터 | 0개 추가 |
| 메일함 권한 | 0개 |
| 새 서비스 | 없음 (이미 쓰는 Slack 토큰) |
| 구현 | `slack-collect.sh`(B-1)를 **채널 여러 개** 받게 만들면 끝. 상태파일 스키마는 이미 `channels: {}` 형태라 구조 변경도 없다 |

> 🟡 **2026-08-12 수정.** 260811 싱크 핵심논의 6에 따라 **착지점이 바뀐다.**
> `vault/08-sales/`(wiki)로 직행하는 게 아니라 **raw로 들어가서 ingest를 거쳐** wiki가 된다.
> Slack은 투입구이지 인입의 중심축이 아니다 — 사람이 직접 raw에 파일을 놓아도
> 똑같이 동작해야 한다. → [[260811싱크-반영-재설계과제]] §5
>
> ```
> 기존:  #sales ──▶ vault/08-sales/            (wiki 직행)
> 수정:  #sales ──▶ raw/slack/sales/ ──ingest──▶ wiki/sales/
> ```

**⚠️ 선행 조건 — 지금의 플러그인으로는 할 수 없다**

`slack-sync` 플러그인은 출력 폴더를 **하나**만 갖는다 (`outputFolder: vault/raw/slack`).
여기에 세일즈 채널을 추가하면 세일즈 메일이 `05-slack`으로 들어가고,
**`05-slack`은 1단계 문서화의 입력이므로 세일즈 메일이 회의록 3종
(전사본·정리본·결정사항)으로 가공된다.** 원하는 결과가 아니다.

→ **세일즈 채널 수집은 B-1(`slack-collect.sh`) 구현이 선행돼야 한다.**
그래야 채널별로 다른 폴더에 보낼 수 있다. → [[자동화-스크립트개편-설계]] §5-0

**필요한 확인 2가지**

1. 세일즈 내용이 들어오는 Slack 채널 이름 — `#sales`인가, 다른 이름인가?
2. 그 채널이 **비공개(private)** 인가? 비공개면 자동화 봇을 채널에 초대해야 읽을 수 있다.

> B(공용 메일함)로 갈 조건: 세일즈 담당이 Slack에 올리는 단계를 **없애고 싶을 때**.

### 4-3. 링크 규칙 [제안]

```
  A) 짧은 이름   [[project-summary]]
  B) 상대 경로   [[260731-노션활용강의-정리본|정리본]]
```

| | 장점 | 단점 |
|---|---|---|
| A 짧은 이름 | 파일을 옮겨도 안 깨짐 | 같은 이름 파일이 두 개면 모호해짐 |
| B 상대 경로 | 정확히 하나를 가리킴 | **폴더를 옮기면 깨진다** |

**제안 규칙**

1. **기본은 A (짧은 이름).** vault 안에 같은 이름 파일이 없도록 유지하면 A가 항상 안전하다.
2. **B는 회의 3종 문서 상호 링크에서만 유지.** 파일명에 날짜가 들어가 충돌 위험이 없고, 이미 자동 생성 템플릿에 박혀 있다.
3. **표시 이름은 `|`로 붙인다.** `[[260731-노션활용강의-정리본|정리본]]` — 본문 읽기가 쉬워진다.
4. **새 문서를 만들면 관련 허브에서 역링크를 건다.** 링크 없는 문서 8개는 사실상 검색으로만 도달 가능하다 = 묻히는 문서다.

> ✅ 지금 고칠 것 1건: `_템플릿-가이드.md`의 `[[index]]` → `05-slack/`에 `index.md`를 만들거나 링크를 지운다.

### 5-2. ⚠️ 발견 — 결정 번호가 태그로 오인식되고 있다

본문에 "결정 `#9`는 ~", "#3과의 관계" 처럼 쓴 표기가 **진짜 태그로 등록된다.**

```
  #1  #2  #12  #14   →  태그 아님 ✅
                        (Obsidian 태그는 숫자만으로 구성될 수 없음)

  #9는  #3과  #10의  #12로  #12가  #3의  #3에  #3과의
                     →  전부 태그로 등록됨 ⚠️  (8종 · 11회)
```

Obsidian 태그 창을 열면 `#9는`, `#3과` 같은 쓰레기 태그가 목록을 채운다. **실제 태그(`#결정됨` 3종)보다 오염 태그가 더 많다.**

**고치는 법** — 본문 표기를 바꾼다.

```
  ✗  결정 #9는 ~이다
  ✓  결정 9번은 ~이다        (또는 `#9`처럼 백틱으로 감싼다)
```
