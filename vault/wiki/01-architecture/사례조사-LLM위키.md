# 사례 조사 — 다른 곳은 어떻게 만들었나

> 260813 회의(00:06) 지적: *"규영 님은 그런 거에 대한 거 하나도 없이 그냥 감각적으로
> 뭔가를 하려고 하다 보니까"* / *"저는 한 10개 이상 찾아보는 것 같은데"*(20:07)
>
> 맞는 지적이다. 카파시 원문 하나만 읽고 만들었다. 이 문서가 그 조사다.
>
> 조사 축은 이준범이 실제로 물은 것들로 잡았다 —
> **어떤 스킬을 만들었나 / 팀으로 어떻게 쓰나 / 싱크를 어떻게 풀었나 / 철학이 뭔가.**

## 0. 조사해서 알게 된 것, 세 줄

1. **스킬 개수가 우리와 자릿수가 다르다.** 우리 4개, 많은 곳은 26개·40개 도구.
2. **팀 싱크는 아무도 제대로 안 풀었다.** 대부분 "1인용"이라고 명시한다.
   **딱 한 곳만 예외**고, 그 방식이 우리가 참고할 만하다 (§4).
3. **"Obsidian 앱은 런타임 의존이면 안 된다"가 이미 업계 결론**이다 (§3).
   이준범이 어제 말한 것과 정확히 같다.

## 3. Obsidian 앱 의존 — 이미 업계 결론이 났다

> **2233admin**: *"No Obsidian required at runtime. The `filesystem` adapter is always available"*
> — 컴파일러와 MCP 서버가 **마크다운 파일을 직접** 다룬다. Obsidian 은 **선택적 IDE**일 뿐이다.

이준범이 어제 말한 것과 같다.

> 이거의 제일 큰 단점은 **옵시디언이 떠 있어야 돼.** (260813, 28:40)
> 저는 직원들한테 **옵시디언 세팅을 시킬 것 같지는 않거든요.** (29:17)

**우리 현황**: `obsidian-git` 플러그인이 GitHub 반영을 맡고 있다 = **앱 의존.**
개편안 B-2(스크립트가 직접 커밋·푸시)가 정확히 이 방향인데 아직 미구현이다.

> 참고: 다른 프로젝트도 같은 함정을 지적받는다 — *"WebSocket 어댑터는 Obsidian 이
> 실행 중이어야 한다"* 는 이유로 실시간 양방향 싱크가 안 된다는 평가가 있다.

## 4. 🔴 팀 싱크 — 여기가 핵심이다

이준범의 최대 관심사다.

> **제일 고민되는 게 싱크예요.** 깃으로 하게 되면 실시간성이 없잖아요 (23:19)
> 내가 회의록을 올리고 **다른 사람이 그 회의록을 볼 때까지의 전 과정을 막힘없이
> 설명할 수 있어야 돼요. 이게 운영이에요.** (43:38)

| 사례 | 팀 지원 |
|---|---|
| ekadetov | **없음** — 협업·다중 사용자 언급 자체가 없다 |
| green-dalii | **없음** — *"단일 vault 모드"*. 충돌 해결·권한 모델 없음 |
| upnorth.ai | **없음** — 개인 지식베이스 전제 |

| Fulkerson | **부분** — 개인/업무 스킬을 분리해 **업무 스킬만 팀에 배포** |

### 2233admin 이 푼 방식 — 우리가 참고할 만하다

| 장치 | 내용 |
|---|---|
| **PR 리뷰로 공유** | *"Shared team memory moves through PR review"* — 팀 기억은 **PR 을 거쳐** 들어온다 |
| **작업자 스코프** | `VAULT_MIND_ACTOR` 환경변수로 메모리·작업 항목을 사람별로 가른다 |
| **사람별 메모리 경로** | `10-Projects/<project>/agents/<actor>/memory/` |
| **동시 쓰기 안전** | **60초 TTL 어드바이저리 락** — 여러 에이전트가 같은 vault 에 동시에 쓸 수 있다 |
| **설정 상속** | `session > workspace-project > vault > user-device > product default` |

**두 가지가 특히 눈에 띈다.**

- **락(lock)**: 우리는 충돌이 나면 사람에게 넘긴다. 이쪽은 **애초에 겹치지 않게** 만든다.
- **작업자 스코프**: 이준범이 *"계정 하나만 있으면 무슨 의미가 있어요? 누가 뭘 어떻게
  하는지 로그로 남기기 위한 건데"*(260811, 15:16) 라고 한 것과 같은 발상이다.

### 그래도 남는 것 — 실시간성

**아무도 git 의 실시간성 문제를 풀지 못했다.** Obsidian Sync 조차
*"Google Docs 식 실시간 공동편집을 지원하지 않는다"* 고 명시한다.

→ **"실시간을 포기하는 대신 무엇으로 보상할 것인가"** 가 설계 질문이지,
"실시간을 어떻게 만들까"는 답이 없는 질문으로 보인다.

## 5. 🔴 Obsidian 을 쓰지 말아야 할 이유 — 조사 결과

> 이준범(260813, 53:51): **옵시디언을 쓰면 안 되는 이유가 있을 수도 있잖아요.**
> 도입하지 않아야 되는 이유가 있다면 그게 뭔지를 고민해 봐달라고 한 적이 있었을 거예요.

[LeafWiki 의 반박](https://leafwiki.com/blog/obsidian-is-not-a-team-wiki/) 이 이 질문에 정면으로 답한다. **우리 상황에 그대로 걸린다.**

| 지적 | 우리 상황 |
|---|---|
| *"새 사람마다 Git 이 필요하고, 클론해야 하고, Obsidian 을 깔아 폴더를 지정해야 한다. **글 한 줄 쓰기 전에 세 단계**"* | 🔴 그대로 해당. 설계문서 §12-5 의 온보딩 문제 |
| *"두 사람이 같은 파일을 동시에 고치면 마크다운 머지 충돌이 난다. **팀 대부분은 그걸 풀 능력이 없다**"* | 🟡 `resolve-conflict` 스킬로 완화. 근본 해결은 아님 |
| *"'그 페이지 링크 좀 보내줘' 하면 답이 GitHub URL 이다. **브라우저에서 열어 고칠 수 있는 페이지가 아니다**"* | 🔴 그대로 해당. 지금 이준범에게 파일을 첨부해 보내고 있다 |
| *"Obsidian Sync 는 기기 동기화지, **역할·접근제어·브라우저 인터페이스가 있는 공유 워크스페이스가 아니다**"* | 🔴 그대로 해당 |

**인정할 것**: 같은 글이 Obsidian 의 강점도 명시한다 — 로컬 우선, 플러그인 생태계,
그래프 뷰, **락인 없는 평문 마크다운**.

**따라서 판단은 이렇게 갈린다.**

```
"팀 위키" 로 쓰려면          → Obsidian 은 나쁜 선택이다 (위 4가지)
"LLM 의 작업 공간" 으로 쓰려면 → 평문 마크다운 + git 이 오히려 강점이다
```

이준범의 입장(*"직원들에게 옵시디언 세팅을 시킬 것 같지 않다"*)은 **후자**다.
사람은 Orca·Claude 로 접근하고, Obsidian 은 안 깔아도 된다. 그러면 위 4가지 중
1·3·4 가 상당 부분 무력화된다 — **애초에 사람이 Obsidian 을 안 쓰니까.**

> 이게 우리가 답해야 할 "철학"의 실체로 보인다.
> **우리는 Obsidian 을 위키로 쓰는 게 아니라 "LLM 이 읽고 쓰는 마크다운 저장소"로
> 쓴다.** 그러면 LeafWiki 의 지적 대부분이 우리 얘기가 아니게 된다.

## 6. GitLab 핸드북 — 전사 운영의 원형

| 원칙 | 내용 |
|---|---|
| **핸드북 우선** | 어떤 변경(프로세스·정책·결정)이든 **문서화가 먼저**고 그다음이 소통·실행 |
| **찾아보기 우선** | *"물어보기 전에 핸드북에서 찾아보라"* — 실시간 소통 의존을 줄인다 |
| **MR 로 갱신** | 살아 있는 문서를 **머지 리퀘스트로** 계속 고친다. 소유자가 명확하다 |
| **공개** | 직원·고객·경쟁사 **누구에게나 공개** |
| **규모** | 2,700+ 페이지로 1,500+ 명이 **셀프서비스** |

**우리에게 유효한 것 둘**

1. **"핸드북에 없으면 존재하지 않는다"** — 이준범의 *"레포만 있으면 누가 와도
   일할 수 있게"*(260811, 1:00:15) 와 같은 사상이다.
2. **MR 로 갱신** — 2233admin 의 *"팀 기억은 PR 을 거쳐 들어온다"* 와 같다.
   우리는 지금 `main` 에 직접 쓴다. **재고할 지점이다.**

**유효하지 않은 것**: GitLab 은 **브라우저에서 열리는 웹 핸드북**이다.
우리는 그게 없다 (§5 의 세 번째 지적).

## 8. 회의록 용례 — upnorth.ai 가 우리와 같다

우리와 같은 문제(회의록)를 다룬 유일한 사례라 구조를 그대로 옮겨 적는다.

```
raw/meetings/              ← 원본 전사본 (immutable)
wiki/people/<name>.md      ← 사람마다. 참석 회의·역할·**미완 약속(open commitments)**
wiki/projects/<project>.md ← 프로젝트마다. 최근 활동
wiki/decisions/<date>-<slug>.md  ← 결정 하나당 한 장
```

**추출 규칙을 `CLAUDE.md` 에 적어둔다:**

> *"결정이란 다음에 해당하는 진술이다 — '우리가 정했다', '합의했다', '이걸로 가자',
> '계획은 …이다'"*

**lint 가 잡는 것:**
- 회의 간 **모순**
- **30일 넘은 미완 약속**
- **한 회의에만 등장한 고아 인물**

우리와의 차이가 분명하다. **우리는 회의 단위로 3종 문서를 만들고 끝**나는데,
이쪽은 **사람·프로젝트·결정 단위로 페이지가 누적**된다.
*"이준범 님이 최근에 뭐라고 하셨지"* 를 물으면 `wiki/people/이준범.md` 한 장이 답한다.
