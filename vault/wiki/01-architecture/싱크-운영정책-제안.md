# 싱크 운영 정책 (제안)

> **읽는 사람**: 이준범 · 검토 기한 주말 (8/15~16)
> **요청받은 것** (0813): *"다른 팀, 다른 회사는 어떻게 적용시키고 있고 우리는 어떻게
> 하는 게 좋을까에 대한 설득력 있는 문서"*

---

## 0. 결론 먼저

**1. 우리는 "싱크"라는 한 단어로 서로 다른 세 문제를 부르고 있었다.** 미팅에서 합의가
안 된 이유가 이것이라고 본다. 나눠 보면 각각 답이 다르다.

**2. 직원이 Obsidian 을 안 쓴다면 직원 기기에는 사본이 없고, 사본이 없으면 싱크할 게
없다.** 싱크가 필요한 건 **에이전트가 도는 기기뿐**이다. 문제의 크기가 줄어든다.

**3. 🔴 대신 지금 완전히 비어 있는 게 있다 — 읽는 길이다.** 이게 준범님이 지적한
*"저장된 정보를 어떻게 사용하게 하겠다"* 의 정확한 공백이다.

> **실측**: 우리 문서의 링크는 **위키링크 511개 / 일반 마크다운 링크 45개**다.
> GitHub 웹에서 문서를 열면 **511개가 전부 죽는다.** 클릭이 안 되고 파란 글씨도 아니다.
> 지금 팀원에게 레포 주소를 주면 **연결이 끊긴 문서 낱장 70개**를 받게 된다.

**4. "하루 한 번"은 절반만 맞다.** 기계 싱크는 자주일수록 낫고(근거 §2), 사람 공유는
하루 한 번이 낫다. 둘은 다른 축이다.

## 1. 세 문제로 나눈다

| | 질문 | 지금 상태 |
|---|---|---|
| **A. 전파** | 내가 쓴 게 남에게 언제 가나 | Obsidian 켜져 있을 때만 10분마다. 꺼지면 **0** |
| **B. 충돌** | 같은 문서를 동시에 고치면 | `resolve-conflict` 스킬 있으나 **실전 검증 못 함** |
| **C. 열람** | 남이 그걸 어떻게 읽나 | 🔴 **없다.** Obsidian 설치가 사실상 유일한 길 |

미팅에서 우리가 붙든 건 A 였다. **그런데 실제로 막혀 있는 건 C 다.**

---

## 2. 다른 회사는 어떻게 하고 있나

### 2-1. GitLab — 사본을 아예 안 만든다

전 직원 핸드북이 **인쇄하면 2,000쪽**이고 전 세계에 공개돼 있다. 방식은 이렇다.

```
서버에 원본 하나 → 브라우저(Web IDE)로 편집 → Merge Request → 리뷰 → 반영
```

**주목할 점: 로컬 사본이 없다.** 마케팅·세일즈 같은 비개발 직군도 페이지 하단
*"Open Web IDE"* 를 눌러 브라우저에서 고치고 MR 을 낸다. git 을 몰라도 된다.

> **그래서 GitLab 에는 A(전파) 문제가 존재하지 않는다.** 원본이 하나뿐이라 전파할
> 대상이 없다. B(충돌)도 MR 단계에서 사람이 본다. 대신 **리뷰 게이트**를 받아들였다.

우리가 "싱크"로 고민하는 문제 상당 부분이 **아키텍처 선택의 결과**이지 필연이 아니다.

### 2-2. Obsidian 공유 볼트 — 실제로 해본 사람들의 보고

커뮤니티 사례를 모아보면 결론이 일관된다.

| 보고된 것 | 출처 |
|---|---|
| obsidian-git 으로 협업하면 **충돌이 끊이지 않는다** | Obsidian 포럼 다수 |
| **"충돌 해결이 편해야 한다 — 엔지니어에겐 괜찮고 나머지 거의 모두에게는 진짜 장벽"** | Obsidian for Teams 2026 |
| 돌아가는 공유 볼트는 전부 **강제가 아니라 규범**으로 돈다 — 노트당 작성자 1명, 폴더별 주인, 주 1회 정원사 | 〃 |
| 🔴 **"그런 규범은 서로 완전히 신뢰하는 몇 명까지 확장된다. 30명·외주 3곳으로는 확장되지 않는다"** | 〃 |
| 실시간 프레즌스가 없다 — 커서도, "누가 입력 중"도 없다 | 〃 |

> **우리 팀은 위키에 등장하는 담당자 기준 6~7명이다.** 위 기준의 *"몇 명"* 안에는
> 있지만 여유는 없다. **지금 규범을 세워두지 않으면 늘었을 때 무너진다.**

### 2-3. 충돌은 얼마나 나나 — 연구 결과

싱크 주기를 정하려면 이 숫자가 필요하다.

| 발견 | 출처 |
|---|---|
| 오픈소스 143개 분석 — **머지 5번 중 1번꼴로 충돌** | Empirical Software Engineering |
| 그중 **75%** 는 사람이 로직을 이해해야 풀렸다 | 〃 |
| 충돌 났던 코드는 버그 확률이 **2배** | 〃 |
| **오래 벌어져 있을수록 충돌 위험이 커진다** | 트렁크 기반 개발 연구 |
| 자주 합치면 **큰 충돌이 사실상 사라진다** | 〃 |

**이게 "하루 한 번"에 대한 답이다.** 하루에 한 번 합치면 하루치 변경이 한꺼번에
부딪힌다. 30초마다 합치면 대부분 그냥 이어붙는다(fast-forward).

> **즉 자주 싱크하는 건 빨라서 좋은 게 아니라, 충돌을 안 만들려고 하는 것이다.**
> 실시간을 목적이 아니라 **수단**으로 봐야 한다.

## 3. 전파(A) — 실측

`git ls-remote`(원격 해시만 묻고 파일은 안 받는 명령) 를 우리 레포에서 5회 실행했다.
**평균 671ms.**

| 폴링 주기 | 하루 실행 | 하루 총 소요 | 평균 지연 |
|---|---|---|---|
| **30초** | 2,880회 | **32분** | **15초** |
| 10분 | 144회 | 2분 | 5분 |
| 하루 1회 | 1회 | 1초 | **12시간** |

노트북 한 대가 하루 32분을 **네트워크 응답 기다리는 데** 쓴다. CPU 는 거의 안 쓰고,
GitHub REST 쿼터와도 무관하다(git 프로토콜이라 쿼터를 안 먹는다).

**전파는 사실상 공짜다.** 여기서 아낄 게 없다.

### 도구 비교 — 앱 없이 도는 것들

| 도구 | 남의 변경 감지 | 충돌 처리 | Obsidian |
|---|---|---|---|
| **git + launchd 폴링** | 30초(우리가 정함) | ✅ 줄 단위 병합 | 불필요 |
| git-auto-sync | 10분 폴링 | ⚠️ rebase 전용, 충돌 시 **싱크 중단** | 불필요 |
| gitwatch | ❌ 없음(보내기만) | — | 불필요 |
| Syncthing | 즉시 | 🔴 **파일 단위 덮어쓰기** | 불필요 |
| Obsidian LiveSync | 즉시 | ✅ | 🔴 **전원 상주** |

**Syncthing 을 뺀 이유가 중요하다.** 수정 시각이 늦은 파일이 이기고, 진 쪽은
`.sync-conflict-날짜-기기.md` 로 이름이 바뀐다. 두 사람이 같은 회의록의 **다른 문단**을
고치면 git 은 둘 다 살리지만 Syncthing 은 한 명 것을 통째로 옆 파일로 민다.

→ **문서 저장소에는 git 의 줄 단위 병합이 맞다.** 속도만 보면 Syncthing 이 이긴다.

## 4. 🔴 열람(C) — 여기가 진짜 공백이다

> ⚠️ **이 절은 [[레퍼런스-정밀대조]] 가 부분 수정한다.** stigmergy 는 *"별도 read site"*
> 를 설계에서 **명시적으로 배제**하고 읽기를 MCP 도구(묻고 인용받기)로 준다.
> 팀 6~7명 규모에서는 **웹 발행보다 질의(`ask`)가 먼저**라는 근거다.
> 아래 511개 링크 문제는 **사실 그대로 유효**하나, 1순위는 아니다.

준범님 지적 그대로다 — *"저장된 정보를 어떻게 사용하게 하겠다가 핵심인데 그 내용이
부족한 것 같아요."*

**지금 이 위키를 읽는 길은 Obsidian 을 설치하는 것뿐이다.** 그런데 우리는 동시에
*"직원한테 Obsidian 세팅을 시킬 것 같지는 않다"* (0813) 고 했다. **모순이다.**

GitHub 웹으로 보면 되지 않나 — **안 된다.** 위 실측대로 위키링크 511개가 전부 깨진다.
GitHub 은 `[[문서명]]` 을 링크로 렌더하지 않는다. 문서끼리 이어져 있는 게 이 위키의
전부인데, **그 연결이 안 보이는 순간 낱장 70개**가 된다.

### 선택지

| | 무엇 | 비용 | 위키링크 |
|---|---|---|---|
| **Quartz** | 볼트를 정적 사이트로 빌드 → GitHub Pages·Cloudflare | 무료, 초기 30~60분 | ✅ 변환됨 |
| **MkDocs (Material)** | GitHub Actions 로 자동 발행 | 무료 | ✅ 플러그인 |
| Obsidian Publish | 공식 | 연 $96~120 | ✅ |
| GitHub 웹 그대로 | 아무것도 안 함 | 0 | 🔴 **511개 깨짐** |

**GitLab 도 핸드북을 정적 사이트로 발행한다.** 레포를 직접 읽게 하지 않는다.

> **제안**: 읽기는 웹, 쓰기는 에이전트. 읽기 전용 웹이 생기면 **팀원 대부분은 사본이
> 필요 없어지고, 따라서 싱크 대상에서 빠진다.** A 문제가 저절로 작아진다.

## 5. 그래서 제안하는 운영 정책

### 5-1. 사람을 세 부류로 나눈다

| | 누구 | 무엇을 설치 | 싱크 |
|---|---|---|---|
| **읽는 사람** | 대부분의 팀원 | **아무것도** | 없음 — 웹은 항상 최신 |
| **쓰는 사람** | 회의를 넣는 사람 | Orca + git | 에이전트가 push |
| **보는 사람** | 그래프뷰·백링크가 필요한 사람 | Obsidian (선택) | 30초 폴링 |

**"전원이 같은 걸 설치한다"를 버린다.** 이게 지금까지 논의가 막힌 지점이었다.

### 5-2. 기계 싱크와 사람 공유를 분리한다

```
기계 싱크 (git)      30초    ← 충돌을 안 만들기 위해. 알림 없음. 사람은 모름
사람 공유 (슬랙)     하루 1회 ← 알림 피로 때문에. "오늘 이런 게 들어왔습니다"
```

**준범님의 "하루 한 번"은 아래 줄에 채택한다.** 위 줄에 적용하면 §2-3 연구와 충돌한다.

### 5-3. 충돌은 규범으로 막는다 — 사후 처리보다 먼저

돌아가는 공유 볼트는 전부 규범으로 돈다(§2-2). 우리도 세 개만 정하면 된다.

| 규범 | 왜 |
|---|---|
| **회의록은 그 회의를 넣은 사람이 쓴다** (노트당 작성자 1명) | 같은 파일을 둘이 안 건드리게 |
| **`index/`·`log/` 는 손으로 안 고친다** (자동 생성) | 충돌이 가장 많이 나는 곳 |
| **주 1회 정원사** — 린트 보고를 보고 정리 | 방치하면 무너진다 |

## 6. 아직 답 못 하는 것 — 숨기지 않는다

| | 상태 |
|---|---|
| `resolve-conflict` 스킬이 실제로 도는가 | 🔴 **검증 못 함.** git 을 고른 이유가 병합인데 그게 미검증이다 |
| 웹 발행 시 **비공개 유지** 방법 | Quartz·MkDocs 의 접근 제어를 아직 안 봤다. 회사 문서라 필수 |
| 30초 폴링을 6~7명이 돌릴 때 | 1대 기준만 실측했다 |
| 팀이 15명 넘어가면 | §2-2 기준으로 **규범이 깨지는 구간**. 그때는 GitLab 형(MR 게이트)으로 가야 할 수 있다 |
