# Ask (그거 왜 그렇게 했지?)

## 목표

사람이 **"그거 왜 그렇게 했지?"** 라고 물으면 vault 에서 근거를 찾아
**출처와 함께** 답한다. 규약 정본은 `vault/schema/query-규칙.md` 다.

이 스킬이 없으면 vault 는 메모 무덤이 된다. 쌓기만 하고 꺼내 쓰지 않기 때문이다.

---

## 절대 규칙

```
① 출처 없는 문장은 답변에 넣지 않는다
② vault 에 없으면 "없다" 고 말한다 — 지어내지 않는다
③ personal/ 은 절대 열지 않는다
④ 문서를 고치지 않는다 (읽기 전용)
```

**④를 어기지 말 것.** 답을 찾다가 틀린 걸 발견해도 고치지 않는다. 말로 알리고
사람이 정한다. 고치는 건 `handoff` 스킬의 일이다.

---

## 순서

### 1단계 — 무엇이 있는지부터 본다

```
vault/index/문서지도.md    층·폴더별 전체 문서 목록
vault/index/회의.md        회의별 3종 문서 (빠진 것도 표시됨)
```

전체를 grep 하기 전에 목차를 먼저 읽는다. 어떤 회의가 있었는지 알면 검색 범위가 좁아진다.

### 2단계 — 순서대로 찾는다

| # | 어디 | 언제 |
|---|---|---|
| 1 | `wiki/05-meetings/결정사항/` | 항상 먼저. **결정은 여기가 정본** |
| 2 | `wiki/05-meetings/정리본/` | 맥락·반대 의견·폐기된 대안 |
| 3 | `wiki/00-overview/`, `wiki/01-architecture/` | 설계 의도, 현재 구조 |
| 4 | `wiki/03-notes/questions.md` | **이미 "모른다"고 기록된 것인지** |
| 5 | `vault/schema/` | "왜 이런 규칙인가" |
| 6 | `vault/raw/` | 위로 안 풀릴 때만. 원문 검증용 |

`raw/` 를 마지막에 두는 이유: 전사본은 길고 오탈자가 많다. 정리본이 이미 해석해
둔 결과물이므로 해석본을 먼저 본다.

### 3단계 — 질문 종류를 판별한다

| 종류 | 신호 | 답에 반드시 넣을 것 |
|---|---|---|
| **사실** | "뭐 쓰지", "어디 있지" | 현재 값 + 어디에 적혀 있는지 |
| **이유** | "왜", "어쩌다" | 결론 + **반대 의견과 폐기된 대안** |
| **이력** | "언제부터", "누가" | 날짜 + 결정한 자리(회의) + 참석자 |

**"이유" 질문에 결론만 답하면 절반만 답한 것이다.** vault 의 존재 이유가
"왜 그렇게 정했는지"를 남기는 것이므로, 반대 의견까지 정리본에서 찾아 전한다.

### 4단계 — 이 형식으로 답한다

```
**결론 한 줄**

근거 — 언제, 누가, 어떤 자리에서 정했는지

(이유 질문이면) 반려된 대안과 그 이유

출처: [[문서명]] §번호

(해당되면) 아직 안 된 것 / 불확실한 것
```

**"정해졌다"와 "실행됐다"를 반드시 구분한다.** 결정만 있고 작업이 안 끝난 항목이
많다 — 이걸 섞으면 사람이 다 됐다고 오해한다.

## 못 찾았을 때

지어내지 않는다.

```
1. "vault 에 없습니다" 라고 분명히 말한다
2. 어디를 찾아봤는지 밝힌다 (사람이 검색어를 바꿔볼 수 있게)
3. 관련은 있으나 답은 아닌 문서가 있으면 그것만 제시한다
4. 문서 frontmatter 의 owner 를 보고 물어볼 사람을 짚어준다
5. wiki/03-notes/questions.md 에 추가할지 제안한다
```

**5번이 중요하다.** 답을 못 찾았다는 건 기록되지 않은 것을 발견했다는 뜻이다.
questions.md 에 쌓으면 다음엔 답이 있다.

---

## 마지막 — 조회를 기록에 남긴다

답을 준 뒤 **반드시** 한 줄 남긴다.

```bash
python3 .automation/wiki_log.py query "<질문>" --found     --detail "출처 N건"
python3 .automation/wiki_log.py query "<질문>" --no-found
```

두 가지 이유가 있다.

1. **조회율이 이 프로젝트의 핵심 지표인데 지금까지 잴 방법이 없었다** (설계문서 §10).
   이 기록이 곧 측정값이다.
2. **답을 못 찾은 질문 목록이 다음에 채울 곳이다.** `--no-found` 로 남긴 항목을
   모으면 "기록되지 않은 것"이 목록으로 쌓인다. 실패가 자산이 되는 고리다.

> 이건 `log/` 에 덧붙이는 것이라 **읽기 전용 규칙(④)의 예외가 아니다** —
> wiki 문서를 고치는 게 아니라 이력을 남기는 것이다.

## 주의할 함정

| 함정 | 대응 |
|---|---|
| **제안을 결정으로 둔갑시키기** | 설계문서의 **[결정됨]/[제안]/[미결]** 표기를 그대로 옮긴다 |
| 오래된 문서를 최신처럼 인용 | `updated` 를 확인하고 오래됐으면 밝힌다. `review_by` 가 지났으면 경고 |
| 회의 3종 중 하나만 보기 | 결정사항은 짧다. 이유를 물었으면 반드시 정리본까지 본다 |
| 같은 주제의 옛 결정과 새 결정 | 날짜를 비교해 **최신을 우선**하되, 바뀌었다는 사실 자체를 알린다 |
| 문서에 없는 걸 코드에서 추론 | 코드는 "현재 어떻게 동작하는가"지 "왜 그렇게 정했는가"가 아니다. 구분해서 말한다 |

> **공용 팀 캘린더를 쓰기로 했습니다.**
>
> 2026-08-11 김규형 결정입니다. 그전에는 담당자가 누구든 모든 일정이 김규형
> 캘린더 한 곳에 쌓였습니다 — `process-slack-docs.sh` 52행에 캘린더 ID 가
> 하드코딩돼 있었기 때문입니다.
>
> 반려된 대안이 둘 있습니다. 담당자를 참석자(attendee)로 넣는 방식은 커넥터가
> 그걸 지원하는지 불확실해서, 팀원마다 커넥터를 연결하는 방식은 자동화 머신
> 1대 원칙(260803 결정 11번)과 충돌해서 접었습니다.
>
> 출처: [[전체-구조도]] §1-6, [[oao-wiki-설계문서]] §12-8
>
> **아직 안 된 것**: 캘린더 생성과 ID 반영은 미완료입니다. 사람이 브라우저에서
> 만들어야 합니다.

결론 → 근거 → 반려된 대안 → 출처 → 미완료. 다섯 조각이 다 있다.
