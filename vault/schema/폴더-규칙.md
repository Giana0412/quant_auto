# 폴더 규칙

> **이 문서를 포함한 `schema/` 의 모든 문서는 사람이 정한다.** 에이전트는 여기 적힌
> 규칙을 따르기만 하고 고치지 않는다. 규칙을 바꾸려면 사람이 이 문서를 고쳐야 한다.

---

## ⚠️ 규칙을 바꿀 때 — 여기만 고치면 동작은 안 바뀐다

에이전트가 **실제로 읽는 파일은 레포 루트의 `CLAUDE.md`** 다. Claude Code 가 세션
시작 시 자동으로 로드하며, `vault/` 안에서 실행해도 상위로 올라가 찾는다.

```
사람이 보는 것     vault/schema/ 문서 7종   ← Obsidian 에 보인다
에이전트가 읽는 것  /CLAUDE.md              ← Obsidian 에 안 보인다 (vault 밖)
```

**따라서 규칙을 바꾸려면 두 곳을 같이 고쳐야 한다.**

| | 무엇 | 역할 |
|---|---|---|
| `vault/schema/*.md` | **정본** | 규칙의 전문과 근거. 사람이 읽고 판단한다 |
| `/CLAUDE.md` | **요약본** | 에이전트가 항상 들고 다니는 압축판 |

`CLAUDE.md` 를 요약본으로 두는 이유: 매 세션 로드되므로 짧아야 한다. schema 문서는
사람이 읽으라고 길게 쓴 것이라 통째로 넣으면 실행마다 비용이 붙는다.

> 이 이중 관리는 **잊어버리기 쉽다.** `schema/` 만 고치고 `CLAUDE.md` 를 안 고치면
> 문서와 동작이 갈라진다. 자동 검사(L8)는 [[lint-규칙]] §5 에 후보로 올려 뒀다.

## 1. 다섯 층

```
vault/
├── raw/      원본.       손대지 않는다
├── wiki/     정리된 지식.  에이전트가 갱신한다
├── schema/   규칙.        사람만 고친다
├── index/    목차.        자동 생성 (손으로 고치면 덮어써진다)
└── log/      이력.        덧붙이기만 한다
```

층을 가르는 기준은 주제가 아니라 **"누가 고칠 수 있는가"** 다.

| 층 | 무엇이 들어가나 | 누가 고치나 |
|---|---|---|
| `raw/` | Slack 수집 원본, 회의 전사본 | **아무도** |
| `wiki/` | 정리본·결정사항, 설계·모듈 문서, 미해결 질문 | 에이전트 · 사람 |
| `schema/` | 이 문서, 템플릿 가이드, 프론트매터·링크·lint 규칙 | **사람만** |
| `index/` | 회의 목차, 문서 지도 | 자동 생성 |
| `log/` | 작업 이력, lint 리포트 | 덧붙이기 / 자동 |

## 2. `raw/` — 손대지 않는 이유

원본을 고치면 **"실제로 무엇이 오갔는가"라는 근거가 사라진다.** 전사가 잘못됐다고
전사본을 고치면, 나중에 "저 사람이 정말 그렇게 말했나"를 확인할 방법이 없어진다.

- 오탈자를 발견해도 **원본은 그대로 두고 정리본에 바로잡아 적는다.**
- 실제로 정리본들은 하단에 *"자동 전사 오기 추정: '규영 님'→김규형 …"* 처럼
  교정 내역을 따로 남기고 있다. 이게 맞는 방식이다.
- 이 규칙은 [[lint-규칙]] **L6** 이 자동으로 감시한다.

```
vault/raw/
├── slack/         Slack 채널에서 수집한 원본 메시지
└── transcripts/   회의 전사본 (ClovaNote 등)
```

## 3. `wiki/` — 폴더 배치

```
vault/wiki/
├── 00-overview/     왜 이걸 하는가        ← 새로 온 사람의 입구
├── 01-architecture/ 시스템이 어떻게 생겼나
├── 02-modules/      코드베이스 모듈별 설명
├── 03-notes/        미해결 질문 축적소
├── 04-persona/      에이전트 성격 정의
└── 05-meetings/
    ├── 정리본/       회의를 이해하기 위한 문서
    └── 결정사항/     실행·추적용. 액션아이템이 여기서 캘린더로 나간다
```

**아직 없지만 계획된 폴더**

| | 언제 만드나 |
|---|---|
| `06-sales/` | 세일즈 필드 정의 확정 후 (설계문서 §12-4) |
| `07-partnerships/`, `08-brand/` | Drive 자산 마이그레이션 승인 후 (§12-3) |

## 4. vault 에 넣을지 말지 — 질문은 하나뿐

**"확정됐는가"는 판단 기준이 아니다.**

```
        ┌─────────────────────────────────────┐
        │  이 문서는 코드가 바뀌면              │
        │  같이 바뀌어야 하나?                  │
        └───────────┬──────────────┬──────────┘
                YES │              │ NO
                    ▼              ▼
         ┌──────────────────┐  ┌──────────────────────┐
         │ 모노레포 docs/    │  │ vault                │
         │ 기능명세·API·QA   │  │ 회의·결정·세일즈       │
         │ 개발규칙         │  │ 파트너십·브랜드        │
         └──────────────────┘  └──────────────────────┘
                                 확정돼도 계속 vault 에 남는다
```

"우리가 왜 그렇게 정했는지"는 코드가 열 번 바뀌어도 그대로 유효하다. 그래서 vault 에 남는다.
**확정됐다고 다른 데로 옮기지 않는다** — 옮기면 기억 창고가 아니게 된다 (260803 결정 13번).

## 5. 절대 넣지 않는 것

| | 어디로 | 왜 |
|---|---|---|
| PDF·이미지·PPT·녹음 등 **바이너리** | Google Drive (링크만 vault 에) | 260803 정리본 2-9 — *"옵시디언에는 MD 파일만"* |
| 개인 데이터 | `personal/` 로컬 전용 repo | 회사/개인 분리 |
| 토큰·비밀번호·자격증명 | `.automation/*.env` (gitignore) | 평문 유출 방지 |
| 계약 원본·고객 개인정보 | Google Drive | 맥락만 vault, 원본은 Drive |

> Slack 수집기는 `.txt` 같은 텍스트 첨부만 본문에 넣고, 나머지는 **Slack 링크만** 남긴다.
> 이 규칙이 코드로 강제돼 있다는 뜻이다.

## 6. 파일명

| 대상 | 규칙 | 예 |
|---|---|---|
| 회의 3종 | `YYMMDD-주제-{전사본,정리본,결정사항}.md` | `260810-주간회의-정리본.md` |
| Slack 원본 | `{YYYYMMDD}_{HHMM}_{작성자}.md` | `20260810_0952_김규형.md` |
| 그 외 | 내용을 바로 알 수 있는 한글 이름 | `자동화-동작구조.md` |

**파일명은 vault 전체에서 겹치지 않게 짓는다.** 링크를 짧은 이름으로 걸기 때문이다
([[링크-규칙]] 참조). 겹치면 어느 문서를 가리키는지 모호해진다.
