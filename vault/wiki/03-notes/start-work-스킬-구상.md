# start-work 스킬 구상 (생각만)

> **결정 사항 아님.** 2026-08-12 Slack 에서 이준범님이 *"start-work 는 나중에 붙는
> 작업이니까 일단은 생각만 해두셔요"* 라고 하셨다. 붙이자는 제안이 아니라,
> 붙일 때를 대비해 지금 아는 것을 적어 두는 문서다.

---

## 1. 요구사항 (이준범님)

> 1. 개인 할일이 자동으로 트래킹 되면 좋겠다
> 2. 슬랙도 자동으로 써주면 좋겠다
> 3. 깃 브랜치 자동으로 메인 풀받으면 좋겠다
>
> 이미 스킬이 존재하긴 하거든요? 스킬 기반으로 더 강조하고 싶은 부분이나
> 빼면 좋겠는 부분 있으면 자유롭게 변형해도 될 것 같아요
>
> 여기서 말하는 start-work 같은 스킬이 저희 데일리 스탠드업 같은 느낌임

**"데일리 스탠드업 같은 느낌"** 이 정의다. 레포 관리 도구가 아니라 **하루를 여는 의식**이다.

---

## 2. 지금 어떻게 돌고 있나 (모노레포 실측)

`company-src/oursymbol/.claude/skills/` 에 `start-work` / `update-work` / `end-work` 세 개가 있다.

| 스킬 | 하는 일 |
|---|---|
| `start-work` | 작업자 식별 → 브랜치·미커밋 확인 → **Slack 이력 조회** → 오늘 할 일 정리 → 브랜치 생성 → Slack 게시 |
| `update-work` | 할 일 항목 추가·삭제 → Slack 재게시 |
| `end-work` | 변경 분석 → `docs/` 구조 검증 → 커밋 → 푸시 → PR → Slack `[오늘 한 일]` |

### ⚠️ 약점 — 할 일의 정본이 **Slack 메시지**다

할 일을 저장하는 파일이 없다. `start-work` 는 `daily-standup` 채널의 최근 30건을
읽어서 `[오늘 할 일 — 이름]` / `[오늘 한 일 — 이름]` 을 파싱하고, **둘을 대조해
미완료를 추정**한다.

스킬 안에 이런 예외 처리까지 들어 있다.

> **인코딩 깨진 메시지 제외**: `?` 문자가 연속 3개 이상 포함된 메시지는
> Windows 인코딩 오류로 생성된 중복이므로 무시한다

**채팅 로그를 데이터베이스로 쓰고 있다는 신호다.** 동작은 하지만
메시지가 밀리거나 형식이 어긋나면 그대로 깨진다.

---

## 3. 통찰 ① — start-work 는 **레포 단위가 아니라 사람 단위**다

"데일리 스탠드업"이면 대상은 **사람의 하루**다. 그런데 사람의 하루는 레포 하나로
끝나지 않는다. 김규형은 모노레포와 vault 를 같이 만진다.

```
레포 단위로 만들면          사람 단위로 만들면
─────────────────          ──────────────────
아침에 start-work 두 번      아침에 한 번
슬랙에 스탠드업 두 개        스탠드업 하나
어느 게 오늘 것인지 헷갈림    명확
```

→ **vault 전용 start-work 를 따로 만드는 것은 답이 아니다.**
기존 스킬이 **여러 레포를 순회**하도록 넓히는 쪽이 맞다.

다만 지금 모노레포 스킬을 그대로 vault 에 쓰면 안 된다. 아래 §5.

---

## 4. 통찰 ② — 할 일의 정본을 Slack 에서 **vault 로** 옮길 수 있다

이게 이 메모에서 제일 중요한 부분이다.

**"개인 할일이 자동으로 트래킹 되면 좋겠다"** 의 데이터가 **이미 vault 에 있다.**

```
회의 → 결정사항 문서의 '## 액션 아이템'  (누가 / 무엇을)
         │
         ▼
   .automation/action-items.json
   status: awaiting_due_date → scheduled → reminded
   due_date, due_time, calendar_event_id
```

회의에서 나온 액션아이템이 곧 그 사람의 할 일이다. 그리고 이미
**기한 문의 → 캘린더 등록 → 당일 알림**까지 도는 파이프라인이 있다
([[자동화-동작구조]] §4).

| | 지금 (모노레포) | 옮기면 |
|---|---|---|
| 정본 | Slack 메시지 30건 파싱 | vault 결정사항 + `action-items.json` |
| 미완료 판정 | 「할 일」에 있는데 「한 일」이 없음 (추정) | `status` 필드 (명시) |
| 깨지는 조건 | 메시지 밀림·인코딩 오류·형식 이탈 | 없음 |
| 출처 추적 | 불가 | **어느 회의에서 나온 일인지 링크** |

**그리고 이건 vault 가 실제로 꺼내 쓰이는 두 번째 경로가 된다.**
첫 번째가 [[query-규칙]]의 `ask` 이고, 두 번째가 이것이다.
*"기억이 조회되면 창고, 안 꺼내 보면 무덤"* 이라고 적어 뒀는데, 아침마다
자동으로 조회되는 경로가 생기는 셈이다.

> 다만 **회의에서 안 나온 개인 할 일**은 여기 없다. 그건 여전히 사람이 적어야 한다.
> 그래서 vault 를 정본으로 하되 **손으로 추가하는 칸도 남겨야 한다.**

## 5. vault 에 쓰려면 — 뺄 것과 더할 것

모노레포 스킬을 그대로 가져오면 안 되는 이유.

### 빼야 할 것

| | 왜 |
|---|---|
| **브랜치 생성** | vault 는 브랜치 없이 `main` 에 직접 쓴다. 비개발자가 브랜치 개념을 몰라도 되게 만든 게 [[oao-wiki-설계문서]] §2 의 전제다 |
| **PR 작성** | 위와 같음 |
| `docs/` 구조 검증 게이트 | vault 엔 다른 게이트가 있다 → [[lint-규칙]] |

### 더할 것

| | 무엇 |
|---|---|
| **vault pull** | 단, **깨끗할 때만 · fast-forward 만.** 충돌이면 멈추고 [[resolve-conflict]] 스킬로 넘긴다 |
| **내 액션아이템 조회** | §4 |
| **lint 상태 한 줄** | 어제 점검에서 몇 건 나왔는지 |

## 6. 주기적 pull 은 **별개 문제**다

Slack 논의에서 start-work 와 "launch 가 주기적으로 pull" 이 같이 나왔는데, 섞으면 안 된다.

```
start-work        하루 한 번.   사람이 부른다
주기적 pull        상시.        기계가 돈다
```

### 누구에게 주기적 pull 이 필요한가

| 사람 | pull 트리거 | daemon 필요? |
|---|---|---|
| **쓰는 사람** | `handoff` 스킬이 이미 push 전에 pull 한다 | ❌ 불필요 |
| **아침에 여는 사람** | start-work 가 pull | ❌ 불필요 |
| **읽기만 하는 사람** | 없음 — Obsidian 켜두고 보기만 함 | ✅ **여기만 필요** |

→ **daemon 은 "읽기만 하는 사람"을 위한 것**이다. 쓰는 사람에게는 이미 경로가 있다.
이 구분을 하면 심바가 말한 A안(세션 종속)/B안(상시 daemon) 논쟁이 상당 부분 해소된다.

### 심바 권고 중 vault 에 그대로 안 맞는 것

심바는 **"작업 repo 와 auto-pull repo 를 분리하라"** 고 했다. 근거는 research 사례
(`data/oursymbol/` 전용 clone 을 `com.oao.research-pull` 이 자동 pull, 컨테이너는
git 을 안 만짐)인데, **그건 읽기 전용 소비 구조다.**

vault 는 반대로 **전원이 쓰는 저장소**라 읽기 전용 미러를 둬도 문제가 안 풀린다.
필요한 건 분리가 아니라 다른 안전장치다.

```
트리가 깨끗할 때만 pull  →  fast-forward 만  →  그 외엔 멈추고 사람에게
```

이건 [[자동화-스크립트개편-설계]] B-3 에 이미 있고, [[resolve-conflict]] 스킬에도
`reset --hard` · `checkout --ours/--theirs` · `push --force` 금지가 박혀 있다.

### 자동 해결 허용 기준은 이미 있다

심바가 만들어주겠다고 한 "auto-resolve 허용/금지 기준표"는 **우리 5층 구조가 곧 그것**이다.

| 층 | 충돌 처리 |
|---|---|
| `raw/` | 사후 수정 금지(lint L6). 충돌 나면 규칙 위반이지 머지 문제가 아니다 |
| `index/` | 생성물. **머지하지 말고 재생성** |
| `log/` | append-only → `.gitattributes` 의 `merge=union` |
| `wiki/` · `schema/` | 사람 의도 → **절대 자동 해결 금지** |

## 7. GitHub Actions 는 지금 규모엔 이르다

이준범님이 *"git actions 로 머지 트리거를 발동시키고 모두가 최신 sync 를 받는 방식"* 을
제안하셨다. 방향은 맞지만 지금은 이르다.

- 4~5명 · 10분 폴링이면 아끼는 게 무의미한 pull 몇 번뿐이다
- Actions 는 로컬 옵시디언을 직접 못 건드린다 — 결국 로컬 수신부가 하나 필요하다(심바도 인정)
- 움직이는 부품만 늘어난다

**다만 Actions 가 진짜 값을 하는 지점이 하나 있다: merge 시 lint 를 돌려 규칙 위반을
PR 에서 막는 것.** 그건 로컬 폴링으로 못 하는 일이다. 붙인다면 그쪽이 먼저다.

## 별건 — 🔴 모노레포 스킬에 Slack 토큰이 평문으로 있다

이 검토 중 발견했다. 스킬 문서 본문에 `curl -H "Authorization: Bearer xoxb-..."`
형태로 **토큰 값이 그대로** 적혀 있고, 네 파일 모두 **git 추적 대상**이다.

```
.claude/skills/start-work/SKILL.md     추적됨
.claude/skills/end-work/SKILL.md       추적됨
.agents/skills/start-work/SKILL.md     추적됨
.agents/skills/end-work/SKILL.md       추적됨
```

- 모노레포를 clone 하는 **모든 사람이 이 토큰을 갖게 된다**
- 스킬 문서는 **에이전트가 읽는 파일**이라, 실행할 때마다 토큰이 세션 기록에 남는다
- vault 자동화가 `curl -K` 설정파일 방식을 쓰는 이유가 정확히 이것이다
  ([[자동화-동작구조]] §4) — 같은 워크스페이스에서 이미 한 번 겪은 사고다

[[oao-wiki-설계문서]] §12-7 에 올라와 있는 "모노레포 자격증명 노출"의 **새 사례**다.
vault 범위 밖이라 고치지 않고 보고만 한다.
