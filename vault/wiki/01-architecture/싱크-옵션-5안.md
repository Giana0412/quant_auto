# 싱크 — 5개 안

> **검토**: 이준범 · 주말 (8/16~17)
> **근거**: [[싱크-운영정책-제안]](실측) · [[레퍼런스-정밀대조]](4대 레퍼런스) ·
> [[사례조사-실사용패턴]](실사용) · [[사례조사-LLM위키]](38건)

**작은 것부터 큰 것 순으로 놓았다.** 1→5 로 갈수록 팀원 부담은 줄고 우리가 만들 게 늘어난다.

---

## 0. 먼저 — 무엇을 고르는 건가

싱크는 한 문제가 아니라 셋이다. 안마다 **어느 것을 푸는지가 다르다.**

| | 질문 |
|---|---|
| **A. 전파** | 내가 쓴 게 남에게 언제 가나 |
| **B. 충돌** | 같은 문서를 동시에 고치면 |
| **C. 열람** | 남이 그걸 어떻게 읽나 |

**지금 우리 상태**: A 는 Obsidian 켜졌을 때만, B 는 미검증, C 는 없다.

---

## 1안. 현행 유지 — obsidian-git

**무엇**: 지금 그대로 둔다. Obsidian 플러그인이 자동 커밋·푸시·풀을 한다.

```
설정 실측: autoSaveInterval 10분 · autoPullInterval 10분 · autoPushInterval 10분
```

| | |
|---|---|
| 전파 지연 | 10분 — **단 Obsidian 이 켜져 있을 때만** |
| 앱 필요 | 🔴 **전원 설치·상주** |
| 충돌 | git 줄 단위 병합. 해결은 사람이 |
| 우리가 만들 것 | 없음 |
| 팀원 부담 | Obsidian 설치 + 계속 켜두기 |

**포기하는 것**: *"직원한테 Obsidian 세팅을 시킬 것 같지는 않다"*(0813) 를 포기해야 한다.
앱을 끄면 전달이 **0** 이다.

> **정직하게**: 이건 선택지라기보다 **현재 상태**다. 그리고 전제와 모순된다.
> 다만 "팀이 아직 작으니 당분간 이대로" 도 근거만 있으면 유효한 답이다.

## 2안. 폴링 데몬 — git + launchd 30초

**무엇**: Obsidian 과 무관하게 도는 백그라운드 잡을 만든다. 30초마다 원격 해시를
확인하고 다르면 받아온다.

```
30초마다  git ls-remote  →  해시가 다르면  git pull
파일이 바뀌면            →  commit + push
```

| | |
|---|---|
| 전파 지연 | **평균 15초** |
| 앱 필요 | ❌ 불필요 |
| 충돌 | git 줄 단위 병합 |
| 우리가 만들 것 | launchd 잡 1개 (**20줄쯤**) |
| 팀원 부담 | git + 잡 설치 (1회) |

### 근거 — 실측

`git ls-remote`(원격 해시만 묻고 파일은 안 받음) 를 우리 레포에서 5회: **평균 671ms**.

| 주기 | 하루 실행 | 하루 총 소요 | 평균 지연 |
|---|---|---|---|
| **30초** | 2,880회 | **32분** | **15초** |
| 10분 | 144회 | 2분 | 5분 |
| 하루 1회 | 1회 | 1초 | 12시간 |

CPU 는 거의 안 쓰고(대부분 네트워크 대기), GitHub REST 쿼터와 무관하다.

### 왜 30초인가 — 속도가 아니라 충돌 때문

> 오픈소스 143개 분석: **머지 5번 중 1번꼴로 충돌**, 그중 **75%** 는 사람이 로직을
> 이해해야 풀렸고, 충돌 났던 코드는 버그 확률이 **2배**.
> 트렁크 기반 개발 연구: **오래 벌어져 있을수록 충돌이 커지고**, 자주 합치면
> 큰 충돌이 사실상 사라진다.

**하루 한 번 합치면 하루치가 한꺼번에 부딪힌다.** 자주 싱크하는 건 빨라서가 아니라
**충돌을 안 만들려고** 하는 것이다.

**포기하는 것**: 팀원 기기마다 1회 설치가 필요하다. "아무것도 안 깔아도 된다" 는 안 된다.

## 3안. 2안 + 에이전트 격리 (worktree)

**무엇**: 2안에 더해, **에이전트는 버리는 git worktree 안에서만 쓴다.** 사람의 작업
폴더를 건드리지 않는다.

```
에이전트  →  임시 worktree 에서 초안 작성  →  검사 통과분만 main 에 커밋
사람      →  자기 폴더에서 계속 작업        (에이전트와 안 부딪힘)
```

| | |
|---|---|
| 전파 지연 | 평균 15초 (2안과 동일) |
| 앱 필요 | ❌ |
| 충돌 | 🔴 **사람↔에이전트 충돌이 구조적으로 사라진다.** 사람↔사람만 남음 |
| 우리가 만들 것 | 2안 + worktree 래퍼 + 착지 검사 |
| 팀원 부담 | 2안과 동일 |

### 근거 — stigmergy

> *"An agent then drafts pages in a **throwaway git worktree**"*
> 세 가지 약속 중 하나: *"a model writes but **code decides what lands**"*
> diff 에 결정적 게이트 8개(`zone` `binary-page` `body-rewrite` `secrets` `pii`
> `frontmatter` `contract` `anchoring`)를 돌려 **통과한 것만 착지**시킨다.

`cortex`(같은 저자)도 같다 — *"the LLM writes, **code verifies** — at every layer."*

> 🔴 **우리 lint 는 게이트가 아니다.** 규칙 문서에 *"자동 수정하지 않는다"* 고 적혀 있고,
> 실제로도 **찾아서 보고만** 한다. 지금 에이전트가 쓴 건 아무 검사 없이 들어온다.

### 왜 지금 필요한가

> *"에이전트가 마크다운을 쓰면 **그럴듯한** 마크다운을 만든다. 그 구조적 잡음은
> 겉치레 문제가 아니다. **하위 단계 전부를 오염시킨다.**"*

**우리는 이미 겪었다.** 템플릿에 프론트매터 규격이 없어서 위반 문서가 무더기로
생성됐고, lint 60건이 한 번에 나왔다.

**포기하는 것**: 에이전트 실행 경로가 한 겹 복잡해진다.

## 4안. MCP 읽기·쓰기 경로 — 사본을 선택사항으로

**무엇**: 위키를 MCP 서버로 노출한다. Claude·ChatGPT·Cursor 어느 클라이언트에서든,
**어느 기기에서든** 읽고 쓴다. 로컬 사본은 **원하는 사람만** 갖는다.

```
사본 없는 사람  →  MCP 로 묻고 쓴다        (설치 0, 싱크 대상 아님)
사본 있는 사람  →  2·3안 데몬으로 싱크     (에이전트 돌리는 기기)
```

| | |
|---|---|
| 전파 지연 | 사본 없는 사람에겐 **개념이 없다** — 항상 최신 |
| 앱 필요 | ❌ |
| 충돌 | 사본 가진 사람끼리만 남는다 (2~3명) |
| 우리가 만들 것 | 🔴 **MCP 서버** — 이 안에서 제일 큼 |
| 팀원 부담 | **없음** — 쓰던 LLM 클라이언트에 연결만 |

### 근거 — 독립적으로 두 곳이 같은 결론

**① stigmergy** — 설계에서 **의도적으로 배제한 것** 목록에 *"**separate read sites**"*
가 있다. 읽기는 MCP 도구 10개(`search_brain` `read_page` `list_entities`
`describe_entity` `ask` 외)로 준다.

**② Hjarni** — 로컬 llm-wiki 로 쓰다가 겪은 문제를 그대로 적어놨다.

> *"처가에 있는데 뭔가 떠올라서 넣고 싶다. **안 된다.**"*
> *"Claude Code 는 파일을 고칠 수 있다. **ChatGPT 는 못 본다. 폰의 Claude 앱도 못 본다.**"*
> 🔴 *"질의하고 기여할 수 있는 **살아 있는 위키를 남에게 건네는 건 불가능했다.
> 정적인 git 레포를 공유할 수 있을 뿐이었다.**"*

**세 번째가 우리 상황 그대로다.** 해법이 MCP 서버였다.

### 이게 준범님 지적에 대한 답이다

> *"저장된 정보를 **어떻게 사용하게 하겠다**가 핵심인데 그 내용이 부족한 거 같아요."*

**실사용 조사에서 사람들은 "묻지" 않고 "시킨다".** Clearwater 는 `/sprint-review-slides`
하나로 JIRA 조회 → 슬라이드 생성 → 저장을 끝낸다(**준비 2시간 → 5분**). MCP 는 그
명령들이 붙는 자리다.

**포기하는 것**: 만들 게 제일 많다. 그리고 **비공개·권한**을 우리가 책임져야 한다.

## 5안. 서버 단일 원본 — 로컬 사본 폐지 (GitLab·PostHog 형)

**무엇**: 원본을 서버에 하나만 둔다. 편집은 브라우저에서. **로컬 사본을 아예 안 만든다.**

```
브라우저에서 편집  →  PR  →  승인  →  머지  →  10~20분 후 사이트 반영
```

| | |
|---|---|
| 전파 지연 | 🔴 **문제가 존재하지 않는다** (사본이 없으니 전파할 게 없다) |
| 앱 필요 | ❌ 브라우저만 |
| 충돌 | PR 단계에서 사람이 본다 |
| 우리가 만들 것 | 정적 사이트 발행 + PR 절차 |
| 팀원 부담 | **설치 0** |

### 근거

**GitLab**: 인쇄하면 **2,000쪽** 넘는 전사 핸드북을 이렇게 굴린다. 비개발 직군은
페이지 하단 *"Open Web IDE"* 로 편집하고 MR 을 낸다. 비기술자용
*"GitLab 101 – a primer for the non-technical"* 을 따로 운영한다.

**PostHog**: 절차가 문서화돼 있다.

> *"Edit this page" → 연필 아이콘 → 고치고 미리보기 → 커밋 → "Create a new branch"
> → "Propose changes" → 승인 → "Squash and merge" → **10~20분 후 반영***
>
> *"**git 설치도 클론도 필요 없다** — 덜 기술적인 역할이라면 이게 기여하기 좋은 방법이다"*

**Clearwater**(실제 회사 팀): 권위로 층을 나눈다 — Tier 1(리더십 승인, **AI 읽기 전용**)
/ Tier 2(기술 기반) / Tier 3(스프린트·회의록) / Tier 4(아카이브, 지우지 않고 내림).
결과: **온보딩 몇 주 → 몇 시간.**

**포기하는 것**: 🔴 **로컬 에이전트 자동화가 성립하지 않는다.** 우리 파이프라인
(Slack 수집 → 회의록 3종 → 인덱스)은 전부 로컬 파일을 전제로 한다. 그리고 stigmergy 는
*"PR ceremony over knowledge"* 를 명시적으로 배제한다 — **에이전트가 쓰는 위키에
사람 리뷰를 매번 거는 건 무겁다**는 반대 근거가 있다.

## 7. 검토했으나 뺀 것 — 왜 뺐는지

| | 왜 뺐나 |
|---|---|
| **Syncthing** | 즉시 싱크·앱 불필요지만 🔴 **파일 단위 덮어쓰기**. 수정 시각이 늦은 게 이기고 진 쪽은 `.sync-conflict-날짜-기기.md` 로 개명된다. 두 사람이 **같은 문서의 다른 문단**을 고치면 git 은 둘 다 살리지만 이건 한 명 것을 통째로 민다 |
| **Obsidian LiveSync** | 실시간 + 청크 병합 + 무료지만 **Obsidian 플러그인** — 전원 상주가 전제. 우리 전제와 정면 충돌 |
| **Obsidian Sync** | 유료·20명 한도. 공식적으로 **실시간 공동편집 미지원** |
| **git-auto-sync** | 데몬으로 돌지만 10분 폴링 + **rebase 전용**, 충돌 나면 그 레포 싱크를 **중단**하고 알림만 |
| **gitwatch** | 보내기만 하고 **받는 쪽이 없다** |
| **웹훅 푸시** | 지연 0 이지만 **1인당 터널**(Cloudflare·ngrok)이 필요 — "설치 안 한다"와 충돌 |
| **CRDT (Yjs·Automerge)** | 에디터에 붙는 라이브러리. **동시 타이핑용이지 파일 싱크용이 아니다** |

## 8. 내 제안

**2 + 3 을 먼저, 4 를 다음에, 5 는 나중에.**

| 순서 | 무엇 | 왜 지금/나중 |
|---|---|---|
| **지금** | **2안 + 3안** | 전제("직원은 Obsidian 안 쓴다")와 현실(앱이 싱크를 함)의 모순을 없앤다. 3안은 **우리가 이미 겪은 문제**(lint 60건)의 재발 방지 |
| **다음** | **4안 (MCP)** | 준범님 지적 *"어떻게 쓰게 할 것인가"* 의 답. 근거가 독립적으로 둘 |
| **나중** | 5안 | 팀 15명 넘어가면. 지금은 로컬 에이전트를 포기해야 해서 비용이 크다 |

### 왜 5안을 지금 안 하나 — 규모 근거

> 같은 사람이 llm-wiki 를 코드로 한 번, 마크다운으로 한 번 구현하고 내린 기준:
> **문서 200개 미만이면 마크다운, 그 이상 감사·스케줄링이 필요하면 코드.**
>
> Obsidian 팀 볼트 보고: *"규범은 **서로 완전히 신뢰하는 몇 명까지** 확장된다.
> 30명·외주 3곳으로는 확장되지 않는다."*

**우리는 문서 73개, 담당자 6~7명.** 아직 가벼운 쪽 구간이다. 다만 여유는 없다 —
**지금 규범을 세워두지 않으면 늘었을 때 무너진다.**

### 어느 안을 고르든 같이 정해야 할 것

| | 제안 |
|---|---|
| **사람 공유 주기** | **하루 1회** — 준범님 안 채택. 기계 싱크(30초)와 **다른 축**이다 |
| 규범 3개 | 회의록은 넣은 사람이 쓴다 · `index/`·`log/` 는 손으로 안 고친다 · 주 1회 정원사 |

> **근거**: PostHog 는 기록과 알림을 나눴다 — *"슬랙보다 이슈를 선호한다. 공개돼 있고
> 코드 워크플로와 이어지니까"* / *"공지는 슬랙 채널로 — **방해받지 않고 일하도록**."*

## 9. 아직 답 못 하는 것

| | 상태 |
|---|---|
| `resolve-conflict` 스킬이 실제로 도는가 | 🔴 **미검증.** git 을 고른 이유가 줄 단위 병합인데 그게 확인이 안 됐다 |
| 4안 MCP 의 권한·비공개 | 회사 문서라 필수인데 설계 안 함 |
| 30초 폴링을 6~7명이 동시에 | **1대 기준만 실측**했다 |
| 5안 정적 사이트의 비공개 유지 | Quartz·MkDocs 접근 제어 미확인 |

> **위키링크 511개 vs 일반 링크 45개** — GitHub 웹에서는 511개가 전부 깨진다.
> 4안(MCP)을 하면 에이전트가 링크를 따라가므로 문제가 줄고, 5안(웹 발행)을 하면
> 변환된다. **1~3안만 하면 이 문제가 그대로 남는다.**
