# 준범님 원온원 (이벤트DB) #1 — 정리본

- 일시: 2026-07-24 (금) 15:08, 103분 5초
- 참석자: 김규형, 이준범

---

## 1. 한줄 요약

이벤트 리서치 파이프라인(discover/enrich/adjudicate/apply)의 실행 구조를 이준범이 화면 공유로 직접 파고들어, "어디서 무엇이 돌고 있는지" 자체가 정리되지 않았다는 점과 수집 데이터의 정확도 문제(중복·오분류)를 확인하고, 개발 방식을 **로컬 개발 → PR → 맥미니 도커 자동 반영**으로 정리한 회의.

## 2. 핵심 논의

### 2-1. 파이프라인 4단계 개요 (김규형 설명)
- 어제(7/23) 저녁 기준 파이프라인은 **수집(discover) → 정리(enrich) → 심사(adjudicate) → 반영(apply)** 4단계
- discover: 등록된 4개 애그리게이터 사이트에서 목록을 뽑고, 그 외 신규 크롤링 대상도 탐색
- enrich: DB 대조로 중복 확인 + 상세 페이지를 열어 디테일 보강 (예: "2026년에 같은 대회가 있었다" 식 판단)
- adjudicate(심사 에이전트): auto / hold / reject로 분류. 공식 사이트 등 출처가 명확한 것만 auto로 통과시키고 나머지는 hold·reject
- apply: DB 반영 직전에 **AI 판단이 틀리지 않았는지 코드로 검증**하는 단계
- 이 외 소스 발굴용 스킬(source scout/vet 계열)까지 포함해 스킬은 총 5개

### 2-2. "지금 무엇이 어디서 돌고 있는가" — 실행 구조 파악 실패
회의의 가장 큰 비중을 차지한 부분. 이준범이 반복해서 요구한 것은 "개발 스펙 — 이 시스템이 어떤 원리로, 어디서 돌아가고 있는지"였고, 이걸 설명하지 못하면 **지훈 님이든 누구든 인수받아 고칠 수 없다**는 지적.
- 김규형은 개인 Claude CLI로 맥미니에 SSH 접속해 작업 중이었고, 처음에는 "맥미니 리서치 플랫폼 안에서 작업 중"이라고 설명
- 확인 결과 Claude CLI가 **도커 컨테이너가 아니라 맥미니 로컬에서** 떠 있었음 → 이준범: 로컬에서 돌면 그 기기의 모든 파일에 접근 권한을 갖게 되므로 위험하다, 반드시 컨테이너 안에서 돌아야 한다
- 작업 위치도 `리서치 스킬` 폴더, `아웃심볼 플랫폼` 폴더, 도커 컨테이너 세 군데로 흩어져 있어 본인도 접속 경로를 정확히 몰랐음 (도커 exec 명령을 함께 쳐가며 겨우 진입)
- 이준범 평가: "로컬에서 하는 작업이 뭐고 도커에서 어떻게 돌아가는지, 그 유기적 관계에 대한 구조나 이해가 안 되어 있는 것 같다"
- 최종적으로 확인된 구조: 맥미니에서 **리서치 도커 컨테이너**가 뜨고, 그 안에 Python·Claude Code CLI·소스코드가 있으며 `run.py`와 새벽 크론도 컨테이너 안에서 돈다. 다만 실제 스킬 파일 수정은 컨테이너 밖 경로에서 이뤄지고 있었음

### 2-3. 헤르메스(심바) 아키텍처와의 불일치
- 이준범: 사전 합의는 "이벤트 리서치는 3파이프라인, **헤르메스 에이전트의 별도 컨테이너 안에서** Claude 모델을 붙여 돌린다"였는데 실제로는 그렇게 되어 있지 않아 보인다
- 김규형이 "심바"를 별개 대상으로 오해 → 이준범: **맥미니의 심바는 헤르메스 에이전트에 떠 있는 프로필**이다
- 상무님이 올려둔 관련 PR(에이전트 실행 환경)을 확인은 했으나, 그 위에서 브랜치를 따 작업한 게 아니라 맥미니 로컬에서만 작업이 진행됨 → "일단 이쪽으로 이식하면 좋겠다"

### 2-4. 수집 정확도 — 중복 대회와 오분류
DB(dev 이벤트 DB)를 직접 열어 7/23 23시경 라이브 실행 결과를 검수. 확인된 문제:
- **아쿠아슬론 챔피언십**: 두 건이 별도 이벤트로 들어옴 → 하나의 이벤트로 묶고 기간은 `start_at`/`end_at`으로 표현해야 함
- **경주 국제 마라톤 vs 경주 마라톤**: 같은 대회인데 이름만 다르게 두 건. start_at이 동일하고, 한쪽은 시작 시각이 23시 15분으로 비정상 (마라톤은 통상 오전 8시 시작)
- **인천 송도 국제 마라톤 vs 국제 하프 마라톤**: 실제로는 3월 개최와 9월 개최로 **서로 다른 대회**인데 둘 다 9월 19일로 수집됨. 김규형은 공식 홈페이지에 두 대회가 따로 있는 걸 확인했으나 날짜 오류는 잡지 못함
- **경청 마라톤 vs 경주 마라톤**: 서로 다른 대회인데 에이전트가 "파싱 오차"로 선언해 병합 판단 → 반대 방향의 오류
- 원칙 정리: 이름이 "하프 마라톤"인 별도 대회가 실제로 존재하는지 확인해야 하고, 같은 대회 안의 하프/풀은 **discipline으로 나눠야지 이벤트를 나누면 안 된다**

### 2-5. 검증 습관의 부재
- 이준범: "에이전트가 '수집 완료됐습니다' 하면 잘 수집됐는지 **DB에 직접 접속해서 확인**해야 어느 부분을 못 잡았고 어떻게 개선할지가 나온다"
- 새벽 5시 크론이 dry-run으로 돌아 DB에 데이터가 안 쌓인 점도 지적 — "드라이런을 몇 시에 돌리는지는 관심 없다. 실제로 데이터가 쌓였는지, 쌓인 데이터의 정확도가 괜찮은지를 보고 싶다"
- 김규형 설명: 크론이 원래 테스트용이라 DB에 안 들어가게 세팅했고, dry-run인데도 슬랙 메시지만 나가는 버그가 있어 새벽 5시 알림이 계속 왔던 것. 이미 수정함
- 개선 검증 방식도 지적됨 — 김규형은 파이프라인 전체 재실행이 오래 걸려 이미 수집된 데이터로 오프라인 테스트만 하고 "결과가 괜찮게 나왔다"고 보고했는데, 이준범이 그 근거를 직접 요구

### 2-6. 유니크화(중복 제거) 위치 — discover로 앞당겨야 함
- 김규형은 토큰 단위 검증(대회명 비교)을 **맨 마지막 단계(apply)** 에 넣었다고 답변
- 이준범 반론: 4개 사이트에 같은 대회(JTBC 마라톤, 제마 등)가 모두 있으면 지금 구조에서는 **enrich를 4번 돌게 된다** → 느리고 낭비
- 올바른 순서: 4개 사이트에서 목록을 각각 뽑아 오늘 날짜 이후 이벤트를 모은 뒤 → **통합해서 유니크한 대회 목록을 만들고** → 그 유니크 목록에 대해서만 enrich
- 즉 "경청 마라톤과 경주 마라톤이 다른 대회인지 같은 대회인지", "제마와 서울 마라톤이 같은 대회인지"를 **수집 단계에서** 알아야 함. 이 유니크화가 discover 스킬 안에 있는지 확인하려 했으나 스킬 파일을 여는 것부터 막힘

### 2-7. 스킬 파일 열람 / 개발 도구 문제
- 스킬 MD 파일을 한 번도 직접 열어본 적이 없다는 게 드러남 (`cat`으로 겨우 열람, 평소엔 VS Code로 요청해서 봄)
- 로컬에 있는 최신본과 컨테이너 안의 버전이 달라 "어느 게 최신인지" 확인에 시간 소요
- 맥미니에서 Claude로 작업했을 때 **워킹 트리가 더러워져 세션이 자동으로 조용히 죽는** 현상 확인
- 회의 중 김규형의 Claude 세션 리밋이 떠서 PR 푸시를 이준범이 대신 올리기로 함

### 2-8. 작업 방식 재정의 (이 회의의 실질적 결론)
- **맥미니 = 실행 전용**, 그것도 도커 안에서만. 개발은 하지 않는다
- 김규형은 **본인 로컬에서** 개발 → GitHub PR → 머지되면 맥미니가 자동으로 clone/pull → 도커 안 스킬 파일에 반영 → run 실행
- 이준범: "환경 세팅은 내가 책임지고 해줄 테니, 규형 님은 5개 스킬의 **고도화만** 하면 된다"
- 김규형 로컬 세팅: Claude CLI 설치(로컬에 전용 설치가 안 되어 있었음, 상무님 계정으로 수령), IDE는 VS Code 대신 **Orca** 설치 권장 — 회의 중 설치 진행
- 우선 지금까지 맥미니 로컬에서 한 작업을 push → PR로 올리고, 이준범이 그걸 보고 머지·검토하기로 함

### 2-9. 기타
- 맥미니에 예전에 깔아둔 Kamal(전사: "케미 스케일") 관련 언급 — 지금은 쓰지 않음
- AWS 토큰이 끊겨 DB 접속이 안 돼 이준범이 새로 발급해줌
- 회의 종료 사유: 녹음 기기 배터리 1% 잔여 + 예정 시간 도과. **enrich 단계 논의는 시작하자마자 중단됨**

## 3. 맥락 / 배경

- 이벤트 리서치 파이프라인은 마라톤 등 대회 정보를 자동 수집해 이벤트 DB에 반영하는 시스템으로, 김규형이 담당해 구축 중이었음
- 이준범은 결과물(수집된 데이터)보다 먼저 **"인수인계 가능한 상태인가"** 를 기준으로 점검했고, 구조 설명 불가 자체를 가장 큰 이슈로 봄
- 이 회의는 같은 두 사람의 **260728 준범님 원온원보다 시간순으로 앞선 회의**이며, 이벤트 리서치 파이프라인에 대한 연속 논의의 첫 회차(#1)로 보임
- 사전에 논의된 아키텍처(헤르메스 컨테이너 + Claude 모델)와 실제 구현 상태의 간극을 확인하는 자리이기도 했음

## 4. 미결정 사항 / 추가 논의 필요

- **enrich 단계 논의 전체가 보류** — 시작 직후 녹음 배터리/시간 문제로 중단. 다음 회의로 이월
- 유니크화(중복 제거)를 discover 스킬 안에 어떻게 구현할지 구체안 미정 — discover 스킬 파일을 함께 확인하려다 끝까지 못 봄
- adjudicate/apply의 판정 기준(경청 마라톤 사례처럼 "다른 대회를 파싱 오차로 오판"하는 문제)을 어떻게 고칠지 미정
- 헤르메스 에이전트 컨테이너로의 이식 시점·범위 미정 ("일단 차차 하고")
- source scout/vet(신규 소스 발굴)은 "4개가 잘 돌아가면 20개로 늘리는 건 어렵지 않다"며 우선순위에서 후순위로 밀림
